    ## Phase 1 — finding and validating a real Poseidon2 implementation

    Entry 74's constraint stands: hand-rolling Poseidon2 round constants without real test
    vectors is a security-critical mistake that fails silently. The candidates entry 74's
    task list suggested were checked, not assumed:

    - **`ultrahonk-no-std` (this project's own bb 5.0.0 verifier fork) does not vendor a
      usable Poseidon2 hash function.** `grep -rn poseidon -i` across both cached checkouts
      turns up only PLONK/Honk gate-selector plumbing (`Q_POSEIDON2EXTERNAL`/
      `Q_POSEIDON2INTERNAL` — verification-key commitments and constraint-relation
      accumulators used to check that a Poseidon2 *gate* inside a proof was satisfied) — not
      a callable "hash these field elements" function. Separately, its Fiat-Shamir transcript
      (`src/transcript.rs`) uses `Keccak256`, not Poseidon2, for the EVM-flavored proof
      variant this project verifies. Confirms entry 74's finding rather than reversing it.
    - **`taceo-poseidon2` (crates.io) was not used, on a specific, checked reason, not a
      vibe.** Its own upstream sibling, `TaceoLabs/noir-poseidon`, describes itself as
      implementing Poseidon2 "in contrast to the existing Poseidon implementation in Noir's
      standard library... utilizing modern optimizations... with all advances in
      cryptanalysis in mind" — i.e. explicitly a *different*, independently-parameterized
      instance from `noir-lang/poseidon`'s, not a compatible one. Real cryptographic evidence
      against reuse, not merely "untested": Poseidon2's round constants are derived from a
      seed encoding the field, state width, and round counts, and two independently-chosen
      instantiations on the same curve are not expected to agree. Not pursued further once a
      directly-confirmed-compatible source was found (below) — no test vectors were computed
      for it, so it should be read as "specifically not the right tool", not "tested and
      failed."
    - **The actual source, found by tracing what `Poseidon2::hash` in
      `noir-lang/poseidon` v0.3.0 really is.** `src/poseidon2.nr` re-exports `pub use
      std::hash::poseidon2_permutation` — Poseidon2 is an ACIR **blackbox function**, not
      Noir source code, so its real definition lives in the Rust toolchain that computes it
      during witness generation, not in any `.nr` file. `gh api
      "search/code?q=poseidon2+repo:noir-lang/noir+language:rust"` located it:
      `acvm-repo/bn254_blackbox_solver/src/poseidon2.rs` (the permutation algorithm) and
      `src/poseidon2_constants.rs` (all 64 rounds × 4 round constants, plus the internal-
      matrix diagonal, as hex literals). Fetched at commit
      `c57152f91260ecdb9faad4efc20abb14b6d2ece7` — confirmed via `nargo --version` to be the
      *exact* commit the locally installed `nargo 1.0.0-beta.22` was built from, i.e. this is
      not "a" Poseidon2 implementation, it is *the* implementation this project's own
      toolchain runs. `t = 4` (state width), `R_F = 8` full rounds, `R_P = 56` partial rounds
      — consistent with the standard BN254 Poseidon2 parameterization.
    - **Ground truth, generated fresh, not assumed.** A throwaway Nargo package
      (`poseidon_vectors`, in this session's scratchpad, discarded — not committed to the
      repo) depending on `noir-lang/poseidon` v0.3.0 and calling `Poseidon2::hash` on seven
      inputs of varying length (1, 2, 3, 4, and two 8-element vectors — one arbitrary, one
      matching `calculate_param_commitment`'s exact shape `[200, anchor, scheme_version,
      pk_hash_0..4]` — plus a zero-input case), run via `nargo test --show-output`. All seven
      printed real field-element outputs.
    - **The Rust port was checked against those seven vectors, and against one more free
      one.** `acvm-repo/bn254_blackbox_solver`'s own test suite embeds an expected raw-
      permutation output for the all-zero state (`smoke_test`) — a ground-truth vector that
      needed no local toolchain to reproduce. A field-for-field, line-for-line Rust port of
      `poseidon2.rs`'s algorithm and `poseidon2_constants.rs`'s literal hex constants
      (`pallets/poseidon2-bn254`, using `ark_bn254::Fr`) was checked against a small `cargo
      run` scratch binary first, then against real unit tests inside the crate itself
      (`cargo test -p poseidon2-bn254`) — **all 8 vectors (7 fresh + 1 embedded) matched
      bit-for-bit**, including the exact 8-element `param_commitment` shape this project
      actually needs. `docs/project/zk-verifier.md`'s bar (real fixtures, not assumed
      compatibility) is met the same way entry 72 met it for `ultrahonk-no-std`.

    `pallets/poseidon2-bn254/src/lib.rs` is the crate this landed as: `no_std`, `alloc`-only,
    exposing `hash(&[Fr]) -> Fr` (byte-identical to `Poseidon2::hash(input, input.len())`) and
    a `hash_bytes(&[[u8; 32]]) -> [u8; 32]` convenience wrapper for on-chain callers. Its own
    `mod tests` (4 tests, `cargo test -p poseidon2-bn254`) is the permanent, checked-in form
    of the validation above — not a scratch script that gets thrown away.

    ## Phase 2 — the real `AnchorProofVerifier`, for the one path it's honest about

    `runtime/src/anchor_verifier.rs` is new. `calculate_param_commitment` mirrors
    `disclosure::calculate_param_commitment` exactly (tag `200`, then `anchor`,
    `scheme_version`, and the 5 `oprf_pk_hashes`, hashed via `poseidon2_bn254::hash_bytes`).
    `check_registration_anchor` is the pure, storage-free core: recompute, then check the
    result against *every* `param_commitments[i]` the already-verified outer proof exposes
    (not just index 0 — a dedicated test, `accepts_when_the_matching_commitment_is_not_the_
    first_slot`, exercises a 2-disclosure-subproof shape to pin this down). `9` unit tests
    (`cargo test -p agora-runtime --no-default-features --features std anchor_verifier`),
    including one that recomputes the exact real-`nargo` 8-element vector from Phase 1 at
    this layer too, and mutation tests over every one of `anchor`/`scheme_version`/each of
    the 5 `oprf_pk_hashes`.

    **A structural finding, not a workaround: `AnchorProofVerifier::verify_registration_anchor`'s
    old signature could not be implemented against.** It took `proof_bytes: &[u8]` — a
    standalone anchor SNARK proof — which is exactly the shape the README's own "why
    `disclosure` exists" section already rules unsafe (`comm_in` is a private witness of the
    outer circuit; a standalone anchor proof can't be authenticated back to a real passport
    proof on-chain). The actual dependency `check_registration_anchor` needs is the *outer*
    proof's already-verified `public_inputs` (which `register_citizen` already has in scope,
    having just called `T::ZkVerifier::verify` with them) plus the 5 `oprf_pk_hashes` (which
    the extrinsic didn't previously take as a parameter at all). Both required a real
    signature/call change, not a workaround inside the old shape:

    - `AnchorProofVerifier::verify_registration_anchor` now takes `(outer_public_inputs:
      &[[u8; 32]], anchor, scheme_version, oprf_pk_hashes: [[u8; 32]; 5])`, no proof bytes.
    - `register_citizen`'s `anchor_proof: BoundedVec<u8, ConstU32<4096>>` parameter is gone
      (there is no separate proof for the `disclosure` path — the whole point of entry 74's
      finding); it's replaced by `oprf_pk_hashes: [[u8; 32]; 5]`.
    - `register_citizen` now also checks each of those 5 hashes directly against a new
      governance-approved allowlist, `OprfCommitteeKeys<T>: StorageMap<(u32, u8), [u8; 32]>`
      (mirrors `AllowedMerkleRoots`'s pattern exactly), via two new `AdminOrigin`-gated calls,
      `set_oprf_committee_key`/`remove_oprf_committee_key` (call indices 11/12). This is the
      README's obligation 1 ("a proof that reuses 4 correct committee keys and substitutes an
      attacker-controlled 5th must still be rejected") — checked in the pallet directly,
      the same place `AllowedMerkleRoots` is already checked, rather than inside the verifier
      trait, so `check_registration_anchor` stays a pure function with no storage coupling.
    - `register_citizen` also now checks `current_date` freshness (the README's obligation
      4): a new `Config::Now: UnixTime` + `Config::MaxAnchorProofAge: Get<u64>` pair, wired to
      `pallet_timestamp` in the runtime (1 day, placeholder pending real timing data, same
      spirit as `ReverificationPeriod`) and to a fixed test clock in the mock.

    **What did *not* get fixed, on the record rather than papered over:**
    `verify_reverification`/`verify_migration` are unchanged — `Poseidon2AnchorVerifier`
    implements them as unconditional `true`, identical to `PassthroughAnchorVerifier`'s
    existing behavior. Tracing why: `reverify_citizen`/`migrate_oprf_scheme`
    (`pallets/pallet-identity/src/lib.rs`) take only a bare proof-bytes blob and never call
    `T::ZkVerifier::verify` or see an outer proof's `public_inputs` at all — the identical
    "no authenticated `comm_in`" problem `disclosure` exists to solve for registration, just
    never applied to those two calls. Fixing this needs the same extrinsic surgery
    `register_citizen` just got (accept the outer `zk_proof`/`public_inputs`, verify them,
    recompute against their `param_commitments`) for both calls — a second, comparably-sized
    piece of work, not attempted this session. Failing closed instead of `true` was
    considered and rejected: neither method can actually check anything real yet, so failing
    closed would only convert "insecure" into "insecure and also everyone is permanently
    locked out of reverification/migration" — an availability regression with no
    corresponding security gain.
