    ## Path chosen, and why the other two were rejected

    The brief asked for three options to be checked in order, not assumed. All three
    were checked:

    - **Hermes `WebAssembly` global**: does not exist. `facebook/hermes#429` has tracked
      "WASM support within Hermes?" as unresolved since December 2020; the first real
      Hermes Wasm work is landing in React Native 0.84 (per Callstack's own release
      coverage) — six minor versions past the `0.74.0` this app is pinned to
      (`package.json`). Confirmed via web search this session, not assumed from prior
      knowledge of Hermes.
    - **Switching `jsEngine` to `"jsc"`**: checked and rejected. JSC's own WebAssembly
      implementation needs JIT to execute, Apple disallows third-party JIT on iOS (the
      existence of Callstack's `polygen` project — built specifically to route around
      this by ahead-of-time-compiling wasm to C via `wasm2c` instead of relying on JSC's
      JIT'd Wasm path — is itself evidence this is a real, known-hard constraint, not a
      guess), and `jsc-android` explicitly disables its own WebAssembly support outright.
      So `jsEngine: "jsc"` would not have produced a *reliably* working `WebAssembly` on
      either platform this app targets.
    - **A native module** (Kotlin/Swift wrapping wasmtime/wasm3/wasmer, or binding
      `oprf-committee-dev`'s C-ABI directly via JNI/Swift interop): not attempted, and
      for a reason specific to this app rather than a general judgment against native
      modules — `committee/` has **no `android/`/`ios/` native project scaffolded at
      all** (confirmed: `find committee -maxdepth 1` has no `android`/`ios` directories;
      `App.tsx`'s own doc comment says so). A native module needs a native project to
      live in; building one from scratch was out of scope for this task, and this
      environment has no Android/iOS SDK or device/emulator/simulator to build or run it
      against regardless (same standing limitation `mobile/`'s own native build is
      blocked on, per `CLAUDE.md`).

    **What was actually built**: the same *idea* `polygen` uses — ahead-of-time-compile
    the wasm module into something the engine can already run, instead of depending on
    the engine's own Wasm support — but simpler for this one small module: Binaryen's
    `wasm2js` (a real, long-standing Binaryen tool, originally built to polyfill
    WebAssembly for engines that predate it, e.g. old Safari/IE11) transpiles the real
    compiled `oprf_committee_dev.wasm` into plain ES-module JavaScript at **build time**.
    The output (`committee/src/crypto/generated/oprfCommitteeCore.js`) has no
    `WebAssembly.*` calls anywhere in it — ordinary arithmetic and typed-array JS — so it
    runs unmodified on Hermes, JSC, V8, or Node, with zero engine-level Wasm support
    required. `committee/scripts/build-wasm-core.sh` regenerates it via `wasm-opt -Oz`
    (208,756 bytes, down from the source module's 241,095) then `wasm2js -O`; the
    unoptimized `wasm2js` output was checked too, for comparison — 8,396,455 bytes vs.
    2,358,982 bytes optimized, both verified byte-identical on the correctness check
    below before the optimized path was kept as the real artifact.

    ## What's real vs. what's still a placeholder

    - **The Rust crypto core itself, rebuilt and re-tested in this session**:
      `oprf-committee-dev`'s full `cargo test --release` (33 lib tests + the
      `wasm_evaluate_query_matches_native_byte_for_byte` equivalence test) passes; the
      `wasm32-unknown-unknown` artifact rebuilds to exactly 241,095 bytes, matching entry
      83's own reported size. Nothing in `oprf-committee-dev/src/ffi.rs` was modified —
      per this task's own constraint, and there was no bug found that would have
      justified touching it.
    - **`committee/src/crypto/wasmCommitteeCrypto.ts`** — the real implementation.
      `buildOprfInput` marshals `sk`/`blindedQuery`/a caller-supplied `seed` into the
      exact 160-byte wire format (`sk` left-padded to 32 bytes, `blindedQuery` at
      `[32,96)`, the hardcoded public `DS_DLOG` constant — copied byte-for-byte from
      `committee-node/src/wasm_host.rs::DS_DLOG_BE`, not re-derived — at `[96,128)`,
      `seed` at `[128,160)`). `evaluateQueryWithSeed` calls
      `oprf_alloc`/`oprf_evaluate_query`/`oprf_dealloc` against the generated core and
      decodes the 192-byte output into `pk`/`dlogProof`/`evaluation`, re-reading
      `core.memory.buffer` fresh on every access rather than caching a view (wasm2js's
      simulated linear memory can replace its backing `ArrayBuffer` on a grow). The
      public `wasmCommitteeCrypto.evaluateQuery` wraps this with a **fresh**
      `crypto.getRandomValues`-sourced seed per call — never a fixed value outside tests,
      per the task's own explicit requirement and `ffi.rs`'s own nonce-reuse warning.
      `index.js` now calls `setCommitteeCrypto(wasmCommitteeCrypto)` at app startup,
      right after the `react-native-get-random-values` polyfill import that
      `wasmCommitteeCrypto.ts`'s `freshSeed()` depends on (documented explicitly in both
      files so the ordering requirement isn't silently reintroduced later).
    - **Correctness — checked against real, independently-computed ground truth, not a
      synthetic vector.** `oprf-committee-dev/src/ffi.rs`'s own
      `tests::sample_input()`/`evaluate_query_matches_direct_native_call` fixture
      (`sk=778899112233`, a real blinded query derived from `beta=4242424242424242`/
      `client_input=999999999999999999999999999`, the real `DS_DLOG` constant,
      `seed=[7u8;32]`) was run through the actual Rust crate via a temporary, throwaway
      `cargo run --example print_fixture` (added, run, then deleted — never committed;
      uses only the crate's existing `pub` API, no source changes) to extract the exact
      160-byte input and 192-byte expected output as hex. Those two hex strings are now
      hardcoded in `committee/src/crypto/CommitteeCrypto.test.ts` as
      `GROUND_TRUTH_INPUT_HEX`/`GROUND_TRUTH_OUTPUT_HEX`. `evaluateQueryWithSeed` on that
      exact input produces **byte-identical** output to the real Rust computation —
      checked both as the full 192-byte blob and field-by-field (`pk`/`dlogProof`/
      `evaluation` separately, so a future regression would point at exactly which piece
      diverged). `buildOprfInput` is checked in isolation too — its output on the same
      inputs matches `GROUND_TRUTH_INPUT_HEX` exactly, catching a field-order/padding bug
      even in a case where it happened not to affect a particular fixture's output.
      Additional tests cover: short-secret-key left-padding, oversized-secret-key
      rejection, wrong-length-`blindedQuery` rejection, the real module's
      `ERR_ZERO_SECRET_KEY`/`ERR_BLINDED_QUERY_NOT_ON_CURVE` error paths surfacing
      through (not swallowed or fabricated into a fake success), and — for the public
      `wasmCommitteeCrypto.evaluateQuery` specifically — that two calls on identical
      input produce the same `pk`/`evaluation` (neither depends on the per-call nonce)
      but a **different** `dlogProof` each time (proving fresh randomness is actually
      being drawn per call, not memoized or fixed).
    - **`npm test` in `committee/`: 30/30 pass** (20 pre-existing + 10 new — 4
      `buildOprfInput` tests, 3 `evaluateQueryWithSeed` tests, 3 `wasmCommitteeCrypto`
      tests), and `npx tsc --noEmit` passes with the new files included.

    ## What was verified vs. what was not — read this before treating this as "done"
