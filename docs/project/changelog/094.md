# #094 — Backing-nullifier proof: circuit + standalone Rust verifier (2026-08-23)

New feature, not a fix: a dedicated ZK proof for **anonymously backing a delegate** — a
Semaphore/nullifier-scheme proof of Merkle-path membership in `pallet-identity`'s
backing-commitment tree (landed in `bae1cbd`), plus a range-checked slot index, over the
`backing_root_secret` a citizen already derived at registration (`ca99c7d`). No passport
parsing, no OPRF committee round-trip — genuinely standalone. Circuit + Rust verifier only in
this pass; no pallet extrinsic calls the new verifier yet (see "Not done" below), matching
entry 093's scope split.

## What was built

- Three new additions to `circuits/oprf-identity-anchor/lib/identity-anchor/src/lib.nr`:
  - `DS_BACKING_TREE_NODE: Field = 210` and `backing_tree_node_hash(left, right) =
    Poseidon2(210, left, right)` — must match, and does match,
    `pallets/pallet-identity/src/lib.rs`'s own numeric tag `210` and
    `backing_tree_node_hash` byte-for-byte (`poseidon2_bn254::hash_bytes` is
    byte-compatible with this crate's `Poseidon2::hash`).
  - `BACKING_TREE_DEPTH: u32 = 32`, mirroring the pallet's own constant.
  - `DS_BACKING_NULLIFIER` (ASCII `"AGORA_BACKING_NULLIFIER_V1"`) and
    `derive_backing_nullifier(backing_root_secret, slot_index) = Poseidon2(DS_BACKING_NULLIFIER,
    backing_root_secret, slot_index)` — per the task spec, deliberately excludes the target
    delegate from the formula (see below).
- One new standalone circuit, `circuits/oprf-identity-anchor/backing-nullifier`: proves
  Merkle-path membership of `Poseidon2(DS_BACKING_COMMITMENT, backing_root_secret)` at a public
  `root`, a range check `slot_index < max_backings_per_citizen` via
  `std::field::bn254::assert_lt` (a genuine full-field comparison — deliberately *not* a
  truncating `as u32` cast, which would let an out-of-range `slot_index` bypass the cap while
  still producing a distinct, unbounded nullifier), and emits `backing_nullifier`.
  `delegate_persona_id` is a plain `pub Field` public input, unused in any constraint — see
  the design-decision section below for why that is sufficient here, unlike
  `delegate-persona`'s `param_commitment` fold.
- `runtime/src/backing_nullifier_verifier.rs`: a new sibling verifier module (not folded into
  `anchor_verifier.rs`, unlike the delegate-persona commitment functions) that performs a
  **genuine standalone UltraHonk pairing check** — reuses `crate::verifier::ultrahonk::verify`
  (widened from private to `pub(crate)`) against this circuit's own embedded VK
  (`runtime/assets/vk_backing_nullifier.bin`), with its own 7-byte envelope (magic `0x42`,
  no `outer_count` field — this circuit has no ZKPassport-style variant family) and its own
  4-field public-input shape check. This is a different shape of module from
  `anchor_verifier.rs`'s recompute-and-check pattern, and deliberately so: `anchor_verifier.rs`
  can skip the pairing check because the outer ZKPassport proof was already verified by
  `crate::verifier` before it runs; nothing verifies a `backing-nullifier` proof first, so this
  module has to.

## Two design decisions the task left open

**1. `delegate_persona_id` binding: plain public input, not a `param_commitment` fold.**
`delegate-persona` (entry 093) had to fold `persona_account` into `param_commitment` because it
rides inside ZKPassport's outer circuit, whose disclosure-subproof interface is a *fixed*
8-field layout with no room for a 9th slot. `backing-nullifier` has no such constraint — it is a
standalone SNARK with a public-input list of its own choosing — and a SNARK's public inputs are
cryptographically bound into the verification equation whether or not the circuit body's
constraints reference them (this codebase already relies on exactly that for
`disclosure`/`migrate-disclosure`'s unused-but-`pub` `service_scope`/`service_subscope`, and
`crate::verifier`'s own `rejects_mutated_public_inputs_for_a_real_proof` test already
demonstrates it empirically against a real bb 5.0.0 proof). So: plain `pub Field`, no fold,
confirmed by a new test in `backing_nullifier_verifier.rs`
(`rejects_a_real_proof_resubmitted_against_a_different_delegate_persona_id`) that flips one bit
of `delegate_persona_id` alone, against a real proof, and gets rejected. This is a deliberate
simplification versus blindly mirroring the persona circuit's pattern, not an oversight — see
`backing-nullifier/src/main.nr`'s module docs for the full argument.

**2. `max_backings_per_citizen`: a checked public input, not a compile-time circuit constant.**
Checked first: `pallet_elections::MaxBackingsPerCitizen` (`pallets/pallet-elections/src/lib.rs`)
is a `StorageValue`, changeable via `set_election_params` under `ConstitutionalOrigin` — a
genuinely governance-mutable "constitutional parameter" today, not a fixed deployment constant.
Baking a bound into the circuit would mean every governance change needs a new circuit, a new
VK, and a hard migration cutover for every citizen's cached tooling — disproportionate for a
value governance is designed to tune freely. So the bound travels as a public input, checked
in-circuit only for internal consistency (`assert_lt(slot_index, max_backings_per_citizen)`); a
future pallet consumer must additionally check it against the live `MaxBackingsPerCitizen`
value before accepting a proof — the same storage-dependent-check split
`runtime/src/anchor_verifier.rs`'s docs already describe for `oprf_pk_hashes`/`current_date`.

## What was NOT done (future phases build on this)

- **No pallet extrinsic calls `BackingNullifierVerifier::verify`.** This pass is circuit +
  Rust-verifier only, matching entry 093's precedent and the task's scope. A future
  `pallet-elections` extrinsic would need to: run `BackingNullifierVerifier::verify(proof_bytes,
  public_inputs)`, then check `root` via `pallet_identity_zk::is_valid_backing_commitment_root`,
  check `delegate_persona_id` matches the extrinsic's own claimed target, check
  `max_backings_per_citizen` against the live `MaxBackingsPerCitizen::<T>::get()`, and record
  `backing_nullifier -> delegate_persona_id` (rejecting or overwriting on resubmission per
  whatever "retarget an existing slot" semantics that pallet chooses to support — the circuit
  itself is agnostic to that choice, since the nullifier is stable across different targets by
  design).
- Same standing limitations as every OPRF-based circuit in this workspace do *not* apply here —
  this circuit needs no committee, ever, and has a genuinely complete round trip already. The
  only real gap is the pallet wiring above.
- No independent cryptographic review.
