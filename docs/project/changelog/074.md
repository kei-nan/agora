# Completed next steps log — entry 74

74. [PARTIAL] **Extended `circuits/oprf-identity-anchor` from log #69's single-committee design
    to log #73's decided 5-independent-committee topology**, and assessed (but did not
    implement) what a real `AnchorProofVerifier` would need to replace `PassthroughAnchorVerifier`.
    Log #73 settled *who* runs the OPRF committee and flagged the circuit extension itself as
    "real circuit-engineering work but an application of an already-proven pattern in this
    codebase, not an open question" — this entry is that application.

    ## What changed, in the circuits

    - `lib/identity-anchor`: `derive_anchor(oprf_output, scheme_version)` is replaced by
      `derive_committee_anchor_term(committee_index, oprf_output, scheme_version)` — the
      per-committee hash `Poseidon2(DS_ANCHOR, committee_index, oprf_output, scheme_version)`
      — and `combine_committee_anchors([Field; 5]) -> Field`, the field-addition combiner. This
      is a literal implementation of log #73's `final_anchor = Poseidon2(..., tag_i, Y_i) +
      ...` design, using `committee_index` (a circuit constant from the loop position, not
      prover data) as the per-committee domain separator rather than inventing 5 new ASCII
      constants — functionally identical domain separation, no magic-constant bookkeeping.
    - `anchor/src/main.nr`: now takes `oprf_proofs: [OPRFProof; 5]` (was a single `OPRFProof`),
      loops over all 5 committees against one shared `identity_input` binding (same
      single-binding-consumed-N-times pattern `migrate` already used for its two evaluations),
      and returns `(anchor, [oprf_pk_hash; 5])` instead of `(anchor, oprf_pk_hash)`.
    - `disclosure/src/main.nr`: same 5-committee loop. Its outer-circuit-facing interface is
      fixed by upstream ZKPassport (8 slots, unchangeable), so all 5 `oprf_pk_hash`es fold into
      `param_commitment` (now an 8-element Poseidon2 hash: tag, anchor, scheme_version, 5×pk
      hash) rather than occupying separate output slots the way `anchor` can afford to.
    - `migrate/src/main.nr`: doubled to `old_oprf_proofs`/`new_oprf_proofs: [OPRFProof; 5]`
      each (10 `verified_oprf` calls total), one shared `identity_input`, returns
      `(old_anchor, new_anchor, [old_pk_hash; 5], [new_pk_hash; 5])`.
    - `query/src/main.nr` is **unchanged** — the OPRF protocol only requires the same blinded
      query reach all 5 committees, which needs no circuit change, only sending the existing
      proof to 5 recipients instead of 1 (log #73: symmetric fan-out, not hash-routed, so no
      per-citizen committee-assignment signal leaks).

    ## What a real `AnchorProofVerifier` would need — assessed, not built

    Went looking for whether `runtime/src/verifier.rs`'s `ultrahonk` module (log #72's real bb
    5.0.0 pairing-check machinery, already proven against genuine passport proofs) could be
    reused directly for an anchor verifier. Finding, and it changes the shape of the remaining
    work:

    - **The `disclosure` path (the one the README already recommends for production) needs no
      new SNARK verification call at all.** `disclosure` rides *inside* the outer proof as a
      recursively-verified subproof — by the time `ZkPassportUltraHonkVerifier::verify` accepts
      an outer proof, `disclosure`'s constraints (including all 5 committees' `verified_oprf`
      checks and the anchor combination) are already checked. What `AnchorProofVerifier` needs
      to do for that path is exactly the four (now five, see the README) obligations the README
      already lists: recompute `param_commitment` from the submitted `(anchor, scheme_version,
      5×oprf_pk_hash)` tuple, check it against the outer proof's `param_commitments[i]`, check
      each of the 5 `oprf_pk_hash`es against a governance-held per-committee-slot key for that
      `scheme_version`, and check `current_date` freshness. No `bb`/pairing math needed for
      this path — it rides on the outer proof's pairing check, already done.
    - **That still has one real, unmet dependency: a Poseidon2 implementation in Rust,
      compatible with `noir-lang/poseidon` v0.3.0's BN254 permutation.** Checked — there is
      none anywhere in this codebase. `grep -rn "poseidon" pallets/ runtime/ Cargo.lock` (case
      insensitive) turns up exactly three doc-comment mentions (`pallet-identity`,
      `pallet-elections`, `pallet-anticorruption`), all describing what should happen, none
      implementing it, and no Poseidon2 crate anywhere in `Cargo.lock`. Recomputing
      `param_commitment` on-chain is impossible without one.
    - **Deliberately not attempted here.** Hand-rolling a from-scratch Poseidon2-over-BN254
      permutation without real Noir/bb-produced test vectors to check it against is exactly the
      kind of security-critical primitive where a subtle mismatch (wrong round constants, wrong
      round count, wrong S-box degree) fails silently — every hash simply comes out different,
      with no error, and every `param_commitment` check would then either always reject genuine
      proofs or (worse, if the same wrong constants are reused symmetrically) accept forged
      ones. This needs either (a) a maintained, audited Rust Poseidon2 crate confirmed
      byte-compatible with `noir-lang/poseidon` v0.3.0 by testing against real `nargo
      execute`-produced hash outputs, or (b) porting `noir-lang/poseidon`'s actual constants
      and permutation by hand and cross-checking the same way. Neither was done in this
      session; flagging it as the concrete next blocker is more honest than shipping an
      unvalidated hash.
    - **The `anchor` (standalone) path, by contrast, would need the full pairing-check
      machinery** the `disclosure` path avoids, plus a real VK asset — `anchor`'s `comm_in` is
      not authenticated back to a certificate-registry root the way `disclosure`'s is (see the
      README's existing "why disclosure exists" section, unchanged by this entry), so a
      standalone `anchor` proof was never the production target; `disclosure` was and remains
      the one worth building a Rust verifier against.

    ## What this doesn't resolve, on purpose

    - **No OPRF committee service exists, now needed 5x over** — unchanged, still the actual
      blocker log #73 named. This entry makes the circuits match the decided topology; it does
      not make anything executable.
    - **`PassthroughAnchorVerifier` is untouched** and still accepts every proof in both build
      paths. Replacing it needs the Poseidon2 dependency above, a governance-held
      per-committee-slot key registry (extending `pallet-identity`'s existing
      `AllowedMerkleRoots` pattern — not designed here), and — separately — real committee
      responses to ever produce a genuine witness to test against.
    - **`disclosure`'s outer-circuit integration is still never been run inside an actual outer
      proof** (log #69's caveat, unchanged): the 8-field layout is carefully derived from the
      upstream interface, not empirically confirmed against a real recursively-verified
      instance.
