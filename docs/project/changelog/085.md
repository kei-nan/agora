# Completed next steps log — entry 85

85. **DKG ceremony orchestration tooling for the OPRF founding phase — the specific open question
    changelog entry 82 flagged and left unresolved ("DKG ceremony mechanics across heterogeneous
    member-owned devices... unresolved").** Entry 82 designed the founding-phase *node*
    architecture (member-owned hardware, one portable Wasm crypto core, an on-chain query/response
    mailbox instead of a relay server) but explicitly scoped out the ceremony that has to run
    *before* any of that steady-state query-answering machinery has a key to use. This entry
    builds real orchestration tooling for that ceremony — genuine process/party boundaries, not
    one function looping `n` times in one process's memory — and is explicit, prominently and
    repeatedly, about what it does not and cannot close: **there is still no real OPRF committee.
    This entry does not reduce that standing blocker (entries 73-83) by one increment.** What it
    closes is narrower and real: a concrete, tested answer to "what protocol would a real ceremony
    run, and does its mechanics actually work when `n` genuinely separate parties run it."

    ## First, the design question this entry had to answer before writing any code

    The task brief asked, correctly, not to assume classical Shamir-style threshold DKG is even
    the right model here without checking the actual code — changelog entry 73's "hashed
    summation" design combines 5 *different* committees' full outputs by hashing and adding, which
    is not threshold secret sharing at all. Reading `pallets/pallet-identity/src/lib.rs`'s real
    storage and extrinsics settles this: `OprfCommitteeKeys` is a `StorageMap<(scheme_version,
    slot), [u8; 32]>` — **one** governance-approved public-key hash per committee, not one per
    member. `submit_oprf_response` accepts a **single** `OprfResponseRecord` per
    `(query_id, committee_slot)` pair (`OprfResponses: StorageDoubleMap`, a presence check, not a
    per-address list) — any one member of that slot's roster answering closes the duty for the
    whole slot, checked only against `CommitteeMembers`' roster membership, with no on-chain
    Chaum-Pedersen verification (the pallet stores the proof bytes for the client/a future
    verifier to check, deliberately out of scope for that additive change). Put together: *within*
    one of entry 73's 5 committees, the design really does need one group public key that many
    members can each independently produce a valid response under — which is exactly what a
    completed Shamir/Feldman DKG produces (one group public key, `n` individually-meaningless-
    alone shares), not a distinct mechanism competing with "hashed summation." `committee.rs`'s
    own doc comment already said as much in passing ("this crate gives each committee one flat
    secret scalar" instead of a real threshold split) but this entry is the first to confirm it
    against the actual mailbox code and build the primitive it presumed. Hashed summation and
    Feldman VSS are answers to two different questions — *across* 5 committees vs. *within* one —
    not alternatives.

    ## What was built

    - **`oprf-committee-dev/src/dkg.rs`** — Feldman verifiable secret sharing / Joint-Feldman DKG
      (Pedersen 1991), the pure math layer: `Polynomial::random`/`eval` (degree-`(t-1)` sampling
      and Horner evaluation mod `BABYJUBJUB_Fr`), `commit` (Feldman commitments `C_k = a_k * G`),
      `verify_share` (the textbook Feldman check `s*G == sum_k idx^k * C_k`),
      `combine_received_shares`, `group_public_key`, and `test_only_reconstruct_secret` (Lagrange
      interpolation at `x=0` — explicitly documented as test/audit-only, never called by the live
      protocol, since reconstructing the full secret anywhere defeats the point of sharing it).
      Every group/field operation reuses `babyjubjub::Point` and `scalar::fr_order()` unmodified —
      no new curve or field code. A single-process unit test
      (`feldman_dkg_produces_a_threshold_consistent_secret`) validates the whole construction
      in-memory first: `n=5, t=3`, every share Feldman-verified, reconstruction from two disjoint
      3-of-5 subsets agreeing with each other and with the published group key, and the
      reconstructed secret plugged into `oprf::evaluate`/`dlog::verify` — both completely
      unmodified — exactly as `committee.rs`'s flat secret would be.
    - **`oprf-committee-dev/src/bin/dkg_party.rs`** — the actual orchestration: run once per
      simulated committee member, each invocation a **separate OS process** with its own address
      space, its own OS-seeded RNG (`std::collections::hash_map::RandomState`-derived, not the
      shared `rand` crate's `getrandom` feature — deliberately avoided so this stays consistent
      with `ffi.rs`'s existing wasm-compatibility constraint on this crate's `rand` feature set),
      coordinating with sibling processes purely through files under a shared `--ceremony-dir`:
      round-1 public Feldman commitments, round-2 per-recipient share files, a barrier-wait
      (poll-with-timeout, matching this project's own established "poll for state" pattern from
      `pallet-courts` jury duty and entry 82's OPRF mailbox) between each round, atomic
      write-then-rename so a poller never observes a torn file, per-party independent computation
      and publication of the group public key (no single trusted combiner — every party computes
      its own copy from purely public data and the harness/an auditor confirms they agree), and a
      roster entry per party. A failed Feldman verification of a received share aborts the whole
      ceremony with a clear error rather than proceeding on unverified material (the known,
      disclosed gap vs. full GJKR: no complaint/justification round to disqualify-and-continue
      instead).
    - **`oprf-committee-dev/tests/dkg_ceremony.rs`** — spawns `dkg_party` as real child processes
      (built once via a separate `--target-dir`, same pattern `tests/wasm_equivalence.rs` already
      uses for its own nested `cargo build`, to avoid lock contention with the outer `cargo test`)
      and checks the result: every party's independently-computed group public key agrees
      byte-for-byte; the roster is complete with no duplicates; a threshold reconstruction from
      two different qualifying subsets of the (test-harness-only-visible — see the file's own
      comment on why a real ceremony must never allow this) private share files produces the
      identical secret, matching the published group key; and that secret is accepted by
      `oprf::evaluate`/`dlog::verify`, called completely unmodified. Run at two scales: **7
      members, 6-of-7 threshold** — changelog entry 73's actual decided founding-group shape —
      runs by default; **35 members, 12-of-35** — entry 73's decided eventual steady-state
      per-committee shape — spawns 35 real OS processes and is gated behind `--ignored` so it
      doesn't slow down every default `cargo test`, and was run explicitly this session
      (confirmed passing, ~16s wall time). A fourth test,
      `ceremony_reports_missing_party_and_times_out_rather_than_hanging`, starts only 4 of 5
      parties (simulating a member never showing up) with a short timeout and confirms the
      survivors fail cleanly — nonzero exit, an error naming the missing party — rather than
      hanging forever; this is the concrete, exercised version of "dealing with a member going
      offline mid-ceremony," not just a claim in a doc comment.

    ## What remains, honestly — read this before anyone mistakes this for progress on the
    standing blocker

    This entry does not, and by design cannot, close entries 73-83's actual named blocker. It
    specifically does not provide: secure channels between real, geographically-distributed
    members (every "private" file here sits on one shared disk on one machine — fine for a test
    harness, unacceptable for a real ceremony); real hardware key custody (shares are written to
    plaintext files; entry 82's own HSM/Secure-Enclave open item is untouched); Sybil-resistant
    member vetting or selection (`--account-id` is an unchecked command-line string); a
    complaint/justification round (a bad share aborts the ceremony rather than disqualifying its
    sender and continuing); resume/replace logic for a member who drops out mid-ceremony (the
    offline-member test proves the failure is *clean*, not that it's *recovered from* — a timed-
    out ceremony must be re-run from scratch); real hardware-RNG entropy hygiene on each member's
    own device; or a path from this tooling's output to an actual on-chain `set_oprf_committee_key`
    call — this tooling stops at a raw group public-key point and a roster of account-id strings
    in files, deliberately not computing the `noir-lang/poseidon`-parameterized hash that call
    expects (that parameterization lives in `pallets/poseidon2-bn254`, a dependency this isolated
    dev workspace deliberately does not take — see its `Cargo.toml` header) or submitting anything
    to chain. See `oprf-committee-dev/README.md`'s new "Founding-ceremony simulator" section for
    the full list in one place, and `src/bin/dkg_party.rs`'s / `src/dkg.rs`'s own module doc
    comments for the same list where the code actually lives.

    **The actual blocker — real independent humans, a real ceremony, real hardware custody, no
    real committee, `OprfCommitteeKeys`/`CommitteeMembers` still empty of anything real — is
    unchanged by this entry**, exactly as entries 73 through 83 have each said in turn.
