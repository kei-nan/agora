[DECISION] **Sybil-resistance / double-registration architecture — resolves log #66's open nullifier-renewal-stability question.** A long design session (human-directed, this file records the resolution) worked through how to stop one real person from voting more than once, given log #66's finding that ZKPassport's default nullifier is document-bound (breaks on passport renewal) and that no deployed passport-ZK system (ZKPassport, Rarimo, OpenPassport/Self, Anon Aadhaar) has actually solved multi-document Sybil resistance — see the research trail below for why each rejected option was rejected, since the reasoning is as important as the conclusion for whoever revisits this.

    **Decided architecture:**
    - **Deployment model: one chain per country, passport-only-from-that-country accepted** (already mechanically supported today by `pallet-identity`'s existing `AllowedMerkleRoots`/country-allowlist check — this is a *configuration* decision, populate the allowlist with exactly one country, not new code). This single fact eliminates the cross-country dual-citizenship Sybil case *structurally* — the hard, undocumented-anywhere-in-the-industry problem the research below found — rather than needing to cryptographically solve it. A dual citizen's second country's passport simply cannot produce a valid proof against a chain that never trusted that country's CSCA roots in the first place. Everything below only has to handle *same-country* duplication (renewal, and the rare case of a government issuing two simultaneously-valid documents to one person).
    - **Mandatory identity anchor, derived from the passport's ICAO-standard "personal number" MRZ field (or an equivalent labeled field — see open questions), run through an OPRF committee, checked via exclusion-proof at every registration attempt.** Not opt-in/opt-out (an opt-out "no stored anchor, just annual re-verification" tier was seriously considered and explicitly rejected in favor of mandatory universal coverage — see rejected-options below for the real trade-off that decision accepts). Mechanism:
      - The personal-number field (ICAO Doc 9303 Part 4, TD3 format: MRZ line 2, **character positions 29–42**, 14 characters, confirmed directly from the primary-source ICAO PDF — not secondhand — see the research log below) is, when a country populates it, a stable government identifier that does **not** change across passport renewal, unlike the document number. It is part of DG1, so it's already covered by the passport's existing SOD signature verification — no new trust anchor needed to authenticate it.
      - **Why a bare hash of this value is unsafe, and why an OPRF is necessary, not optional**: a national ID number has very low entropy (Israel's Teudat Zehut: 9 digits, ~10⁹ possibilities). A plain `Poseidon2(personal_number)` published on-chain is fully invertible by brute force — anyone can precompute the hash of every possible ID number (minutes on ordinary hardware, or hours for a wider format) and reverse any published value back to the real ID, which then cross-references to a real identity via every other database that uses that same ID as a join key (banking, health records, tax records — true in most countries with a national ID system). Adding more stable passport fields (DOB, name) does not fix this: DOB adds only ~15 bits (a 100-year range), and for a *targeted* attack against one specific person, DOB and name are usually already known, so they contribute nothing at all to security in the threat model that actually matters. This is a structural property of every human-manageable government ID field, not an engineering gap — no combination of MRZ text fields clears the ~80-bit floor needed to resist a real attacker.
      - **Why ZKPassport's own default nullifier doesn't have this problem, and why our modification reintroduces it**: ZKPassport's default nullifier is `hash(DG1, e_content, SOD_signature)` — safe from brute force not because the signature is "high entropy" in the abstract, but because an attacker *cannot generate candidate signatures at all* without the issuing government's private signing key; there is no enumeration attack available. That security is exactly why the value changes on every renewal (a signature is computed over data that includes a new document number and dates each time — a hallmark property of digital signatures, not a coincidence). We deliberately traded that document-bound safety away for renewal-stability by switching to the personal-number field; the OPRF's entire job is to buy back the safety that swap gave up, using a party-held secret instead of an unforgeable signature.
      - **OPRF committee, not a single server**: the OPRF secret is threshold-split across multiple independent governance parties (this project already has precedent for exactly this shape of multi-party trust — Elections Commission, Judiciary, Auditors, oracle rotation — none of which are single points of failure today). ZKPassport's own `oprf-auth` circuit already implements a vOPRF-based blinded-query pattern for a different stated purpose (cross-service correlation prevention, via `service_scope`/`service_subscope`); whether it can be repurposed to take the personal-number field as its blinded input instead of its default document-bound nullifier is flagged as an open research question below — proposed, not yet verified against the actual circuit source.
      - **The anchor is checked once, at registration/renewal, and never touches the ongoing voting flow.** It must not appear in, or be derivable from, the per-vote nullifier used for casting ballots — if it did, every vote by the same citizen would become linkable to every other vote by that citizen via the reused anchor value, quietly breaking the receipt-free/unlinkable voting property (MACI/Semaphore) this whole project is built around. What persists across a renewal is the citizen's *eligibility status* (the existing `CitizenIndex`/`TotalCitizens` bookkeeping) — never a log of what they voted on, which the system should not be able to reconstruct in the first place.
      - **Renewal needs only the citizen's current passport — not both old and new.** (An earlier draft of this design during the session wrongly required holding both documents simultaneously, modeled on a cross-document continuity proof; that requirement is now understood to be unnecessary and is explicitly superseded here.) Since the anchor is derived from a field that doesn't change at renewal, recomputing it from the new passport alone reproduces the *same* anchor value already on file — the system doesn't need proof that two different documents belong to the same person, because the anchor computation already produces identical output for both. A "renewal/migration" call therefore takes just the current passport's proof, recomputes the anchor, matches it against the citizen's existing registration, and updates whichever per-session/per-vote nullifier needs updating — no second document, and consequently no need for a biometric cross-check against an old photo either (ordinary single-document face-match, already part of baseline registration, is sufficient).
    - **Scheduled OPRF-scheme rotation, every 4 years, for cryptographic agility.** Rather than betting one committee/scheme on holding up forever (an unreasonable bar for anything permanently published on a public ledger — see the "why data can't really expire" research below), the scheme itself rotates on a fixed cycle, bounding how long any single scheme's security actually has to hold. Mechanics:
      - Rotation is **not** a blank-slate re-registration — citizens keep their eligibility status and, cryptographically, prove continuity via **dual evaluation**: compute the anchor under both the outgoing scheme (`OPRF_V1`) and the incoming one (`OPRF_V2`) from the same personal-number value, with a consistency proof that both came from the same input (never revealing the input itself), checked against both anchor sets. This only works because the *outgoing* committee is still trustworthy (a scheduled, precautionary rotation, not a response to a break) — see the emergency case below for why that assumption doesn't hold there.
      - This dual-evaluation step is piggybacked onto the same periodic re-verification event every citizen already goes through (see below) — no separate UX flow. This also bounds (not eliminates) the "someone tries to double-register during the transition window" risk to at most one re-verification interval, closed automatically at the next check-in — the same bounded-not-eliminated shape as the rest of this design, not a new kind of gap.
      - A **hard cutoff** applies: some fixed period after a rotation, the old scheme's outputs stop being checked/trusted at all, and anyone who hasn't migrated by then loses active status — creating real pressure to migrate promptly.
      - **Emergency rotation, via `pallet-emergency-council`**: if a critical break in the *current* OPRF scheme is discovered or suspected before the scheduled 4-year mark, the outgoing committee's own answers can no longer be trusted for the normal dual-evaluation cross-check (a leaked key could forge a false "not previously registered" response). `pallet-emergency-council`'s existing time-locked emergency powers should be extended to trigger an out-of-cycle rotation in this case, falling back to a temporarily weaker stopgap (e.g., migration-proof-plus-court-backstop only, no continuous anchor check) for just the emergency window until a newly-vetted committee is live — a real, disclosed degraded mode during active incident response, not a silent one.
      - Make the rotation interval itself a governance parameter (matching the existing pattern of tunable constants like `ReferendumDurationBlocks`), not a hardcoded 4 years.
    - **Periodic re-verification, with signal reliability explicitly prioritized** (all three are not equally load-bearing): (1) **passport expiry date** — the primary, universal, ICAO-standard signal, checked at every re-verification independent of anything else; (2) **NFC chip liveness** — a bonus signal in countries whose cancellation procedure happens to disable the chip's antenna (confirmed real practice for corner-punch cancellation generally, but confirmed *uncertain* whether it electronically disables the chip specifically for Israel — no country-by-country guarantee exists, ICAO doesn't standardize cancellation method); (3) **visual/photo invalidity check** — the weakest, most supplementary signal (gameable, inconsistent across ~190 countries' different cancellation conventions: corner clip, hole punch, stamp, page removal), worth having as an extra layer but not to be relied on as equivalent to the other two.
      - An AI-judge review of ambiguous visual evidence (reusing the existing court AI-judge infrastructure rather than building a bespoke, likely-unreliable CV classifier) was proposed as an optional escalation path — flagged open below, since it raises two real, undecided issues: sending a passport photo to a cloud-based AI judge is a genuine departure from "nothing leaves the phone" for passport data, and charging for it risks functioning as a poll tax if it's ever required (not merely optional) to retain voting eligibility. If pursued, keep the automated/free baseline check as the only *mandatory* path, with any paid AI-judge review reserved for a citizen who wants to contest an ambiguous automatic result — the same shape as appealing to a human jury in the existing court system, which isn't paywalled either.
    - **Self-declaration + court backstop for the residual, non-cryptographic gap.** With cross-country dual citizenship eliminated by the deployment model, what's left is narrow: a government accidentally (or corruptly) issuing two simultaneously-valid passports to the same person within one country — something no client-side cryptography can prevent, since both documents would be authentically signed. Citizens self-declare (attest) at registration that they don't hold another currently-valid passport from that country; if later found false, `pallet-courts`' existing `CitizenConduct` case type (already supports filing a case and auto-suspending a citizen via `suspend_citizen_internal` on a guilty verdict — no new pallet logic needed) provides the enforcement path. This is a deterrent-plus-ex-post-remedy, not a prevention guarantee — the same shape every real democracy uses for voter fraud generally.
    - **Why "just make the on-chain data expire" doesn't substitute for any of the above cryptographic reasoning** (a real sub-thread worth preserving): on-chain *current state* absolutely can expire (this pallet already does it — `pallet-emergency-council`'s `on_initialize` auto-expiry of `ActiveEmergency` — and per-citizen expiry blocks are the natural mechanism for the 1-vs-4-year-style cadences discussed here). But the *historical transaction log* is a different thing: the real exposure moment is the instant a transaction is broadcast to the public P2P network, which happens before any pruning/expiry policy is even relevant — any node on the network can capture and permanently retain a copy the moment it's gossiped, entirely outside the protocol's control, and for a national voting system there will almost certainly be parties (election monitors, journalists, researchers) who deliberately run archive nodes precisely because permanent auditability is treated as a *feature* everywhere else in this system. This is not a blockchain-specific quirk — it's the same reason "the right to be forgotten" doesn't really work on the open internet generally. Expiry of current state is worth doing as hygiene; it must not be relied on as the actual security mechanism. That's the OPRF's job, and only the OPRF's.

    **Explicitly rejected, and why (worth preserving so these don't get re-litigated from scratch):**
    - *Weak-field anchor without OPRF* (name+DOB+nationality, or name+DOB alone) — rejected: same brute-force problem as the bare personal-number hash, just with different (and for a targeted attack, often *already-known*) inputs; nationality specifically is actively harmful to include since it's guaranteed to differ across a dual citizen's documents by construction, defeating exactly the case it would need to catch.
    - *Biometric global uniqueness (World-ID-style iris/face matching)* — rejected: requires either centralized biometric capture (incompatible with "nothing leaves the phone") or an MPC/ZK 1:N matching primitive that current research confirms is not deployed at population scale anywhere (see research trail); the one system that does solve this (World ID) has drawn real bans/investigations (Kenya, Brazil, Germany) specifically over the biometric-retention model.
    - *Phone fingerprint sensor as a global identifier* — rejected: structurally impossible, not just impractical. iOS Secure Enclave / Android StrongBox never expose a fingerprint template or hash to any app under any API, by deliberate platform design; there is nothing to extract, on any phone.
    - *Corner-cut/visual-cancellation detection as the primary renewal signal* — rejected as a *primary* mechanism (kept only as the weakest supplementary layer above): ICAO doesn't standardize cancellation method, and confirmed directly from ICAO Doc 9303 Part 4 that only the personal-number field's *position* is standardized, not any visual cancellation convention.
    - *Opt-in/opt-out anchor coverage* (citizen chooses stored-anchor-plus-4-year vs. no-anchor-plus-1-year) — seriously designed, then explicitly overridden in favor of mandatory universal coverage. Recorded honestly: mandatory coverage is not a strict improvement, it's a different trade. It gains uniform Sybil-resistance for the whole population but (a) removes the safety valve for citizens with real elevated personal risk (journalists, dissidents, abuse survivors) who might reasonably prefer avoiding any future-exposure risk over annual re-verification friction, and (b) makes the OPRF committee a substantially higher-value attack target, since a successful compromise would now unmask the entire citizenry at once rather than a self-selected subset. The human decision-maker chose mandatory coverage anyway, consciously — if this gets revisited, that trade-off is the reason to look at, not a claim that mandatory is simply "safer" in every dimension.
