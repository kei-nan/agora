# #096 — mobile: wire the delegate-persona and backing-nullifier crypto (2026-08-23)

Wires the mobile app to the real cryptography built across 2e07f68 (delegate-persona circuit),
ca99c7d/bae1cbd (backing-commitment tree), e31257a (backing-nullifier circuit), and 786b792
(`pallet-elections` consuming both). No mobile code previously referenced any of this — commit
786b792 itself changed `register_as_delegate`/`back_delegate`/`remove_backing`'s on-chain
signatures with mobile call sites left on the old shapes, which would have failed at the chain
boundary with no compile-time warning (the same class of gap `voting.test.ts`'s own doc comment
describes for `submitProposal`).

## What changed

**`mobile/src/chain/keystoreWallet.ts`** gained a second, independently-generated Keystore-backed
keypair (`getOrCreateDelegatePersonaKeypair`), its own random 32-byte seed under its own on-disk
file — deliberately NOT derived from `identity_input`: that value is non-rotatable (fixed by the
passport's own MRZ fields for the document's life), so a persona key derived from it could never
be rotated if compromised, for no benefit — the one-persona-per-citizen property is already
enforced by the ZK nullifier (`DelegatePersonaUsed`), not by how the signing key was generated.
Refactored via a small `createKeystoreBackedKeypairGetter` factory shared by both keypairs rather
than duplicating the load/cache/persist logic a second time.

**`mobile/src/chain/backingNullifierEncoding.ts`** (new): the byte envelope
`runtime/src/backing_nullifier_verifier.rs` expects (`0x42`/'B' magic, 7-byte header — one byte
shorter than the ZKPassport envelope, no `outer_count` field) plus the fixed 4-field
public-input layout (`root`, `delegate_persona_id`, `max_backings_per_citizen`,
`backing_nullifier`), mirroring `proofEncoding.ts`'s relationship to `runtime/src/verifier.rs`.

**`mobile/src/chain/backingTree.ts`** (new): a client-side mirror of `pallet-identity`'s
depth-32 backing-commitment Merkle tree (Poseidon2, domain-separated tags 210/211, identical bit
convention to `certificateTree.ts`'s depth-16 tree but using plain arithmetic instead of bitwise
operators since leaf indices can exceed 2^31) plus real chain-storage reads: a fresh
authentication-path witness for a given leaf index, the current root, and a real
`is_valid_backing_commitment_root`-equivalent check against `BackingRootValidUntil` and the
current block. Deliberately always reads live rather than caching a witness — sibling nodes on
even a citizen's own fixed leaf's path can shift as unrelated citizens register/revoke elsewhere
in the tree, so a witness is only ever valid as of the moment it's fetched (within the pallet's
own retention window).

**`mobile/src/chain/zkProving.ts`** gained `proveDelegatePersona` (a thin wrapper over the
existing `proveRegistration` orchestration, mirroring `proveReverification`/`proveMigration` —
a delegate-persona proof is disclosure-shaped and rides inside the outer ZKPassport proof exactly
like `disclosure` does) and `proveBackingNullifier` (a new, structurally different path: the
backing-nullifier circuit is standalone, proved directly against the `evm` target with no base
subproofs or outer-circuit wrapping, since it's verified the same way the outer ZKPassport proof
itself is — a genuine standalone pairing check).

**`mobile/src/chain/backingState.ts`** (new): a session-only local cache of which backing slot
index a citizen has assigned to which delegate. This is genuinely required client-side
bookkeeping, not a convenience shortcut: under the unlinkable design a `backing_nullifier`
depends only on `(backing_root_secret, slot_index)`, never on the target delegate, so nothing
on-chain can answer "is citizen X backing delegate Y" for any observer — including a citizen's
own future session, which has no way to recover which slot (if any) it pointed at a given
delegate without asking its own wallet.

**`mobile/src/chain/governance.ts`** call sites updated to the new pallet shapes:
`registerAsDelegate` now takes a `personaKeypair` (not the citizen's main wallet) plus the full
delegate-persona proof/OPRF parameter set, matching `register_as_delegate`'s new 8-argument
signature; `backDelegate`/`removeBackingFromDelegate` now take a `BackingProofSubmission` and
record/clear the local backing-slot cache on success; `isBackingDelegate` is now a local lookup
(the old `BackingOf` chain query it used is gone, replaced by the unlinkable nullifier design);
new `fetchDelegatePersonaId`/`fetchMaxBackingsPerCitizen` read the two live values a
backing-nullifier proof's public inputs must be checked against.

**Screens** (`RegisterDelegateScreen.tsx`, `DelegateScreen.tsx`, `DelegateDetailScreen.tsx`)
rewritten from the honest "no separation exists yet" text (df11aaf/d344aa3) to describe the now-
real scheme precisely: delegate identity is a genuinely separate account, backing is a genuinely
unlinkable ZK proof — while stating plainly what is NOT protected (a citizen's chosen display
name is a public choice, not hidden by the protocol; ordinary chain-analysis clues like funding
patterns remain a residual gap; and, like every identity-gated feature in this app, none of it
can actually be exercised until a real OPRF committee exists). Both screens' submit flows follow
`RegisterScreen.tsx`/`RecoverAccountScreen.tsx`'s established pattern: proceed through every real
step (resolve the persona keypair, resolve chain-side proof-input material), then throw a local
`NotImplementedError` at the exact point real Noir proving would need to run, caught and shown as
an "Almost there" info modal rather than a bare failure.

## What was NOT built (and why, honestly)

Real on-device proving for either circuit needs the same two dependencies ordinary citizen
registration is already blocked on: a real on-device Noir prover (`zkProving.ts`'s
`NoirProverUnavailableError`) and a real OPRF committee to answer the query round
(`oprfCombine.ts`'s `combineCommitteeSlotResponses` is a documented, deliberate stub — this pass
did not touch it, and did not attempt to derive `backing_root_secret` or `delegate_persona_id`
locally, since doing so would need exactly the threshold-cryptography code that module documents
as unimplemented for good reason). `zkProving.ts`'s `proveBackingNullifier` and `proveDelegatePersona`
therefore take already-derived secret/proof material as parameters, mirroring `identity.ts`'s
existing convention for `anchor`/`oprf_pk_hashes` (caller-supplies, this module only validates/
encodes/submits). `backingTree.ts` also does not attempt to resolve a citizen's own `leaf_index`
from a real nullifier — `identity.ts`'s `getSigningKeypair` already documents its `nullifierHash`
as a placeholder that won't match the real on-chain value — it exposes
`fetchBackingLeafIndexForNullifier` as a real, ready-to-use lookup for whoever eventually has a
real nullifier to pass it.
