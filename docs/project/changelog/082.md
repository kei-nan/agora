# Completed next steps log — entry 82

82. [DECISION] **OPRF committee node architecture for the founding/bootstrap phase — where and how
    the committee-member software actually runs.** Entry 73 decided the governance model (5
    independent ~35-member committees, hashed-summation combination, 5×7-person founding groups
    before sortition handoff) but left "what does a committee member actually run" unspecified
    beyond citing `TaceoLabs/oprf-service` as the reference implementation. This entry resolves that
    for the **founding phase only** (the 5×7-person groups, not the eventual 35-member sortition-scale
    committees — that handoff's own logistics are explicitly out of scope here, see "Still open"
    below) — arrived at through the same kind of adversarial back-and-forth entry 73's governance
    model went through, with several proposed shortcuts found broken and rejected along the way.
    The rejections are recorded with their reasoning for the same reason entry 73 recorded its own:
    so the next person revisiting this doesn't re-propose them without knowing why they didn't work.

    ## Decided

    - **Committee members run the node on their own hardware — phone, laptop, or a Raspberry
      Pi — member's choice, not a project-rented server.** Motivated by the standing goal of keeping
      the founding phase standalone and free of ongoing hosting cost. Devices are **supplied to
      members, not used as a selection filter**: screening founding-group participants by "do you
      already own reliable hardware" would skew who can serve toward wealthier/more technical
      citizens. Real citizens'-assembly research backs this — sortition panels already see severe
      self-selection bias (typically only 2-5% of those invited participate, skewed by exactly these
      kinds of resource/capability correlates), and the published fix (Flanigan et al., NeurIPS 2020,
      validated on the real Climate Assembly UK) is reweighting the pool, not filtering it further.
      Real government digital-inclusion programs (device-lending libraries, subsidized-device
      programs like ConnectHomeUSA) follow the same principle: equip people, don't select only the
      already-equipped.
    - **One portable crypto core, compiled to WebAssembly, not three separate ports.** The already-
      validated `oprf-committee-dev` Rust logic (BabyJubJub arithmetic, the TACEO Poseidon2 variant,
      Elligator2, Chaum-Pedersen proof generation — see entry 78) compiles once to a `.wasm` module
      that runs identically on phone, laptop, or Pi. This reuses tooling the project already has:
      `agora-runtime` already compiles to Wasm, and the desktop app already embeds a Wasm-based light
      client (`smoldot`). The point is that the sensitive cryptography is validated once and never
      reimplemented per-platform — only the thin host shell differs.
    - **Per-platform shell**: a native mobile app — deliberately **separate from the main citizen
      identity/voting app**, to keep the OPRF secret share's attack surface isolated from the
      general-purpose app most citizens use — embeds a Wasm runtime and calls into the shared
      module. Laptop/Pi run the same Wasm module inside an OCI container (multi-arch: amd64/arm64);
      **balenaCloud** is the proposed fleet-management/update mechanism for those two, since it's
      built for exactly this shape (heterogeneous single-board computers in different members' homes,
      remotely updatable without exposing SSH).
    - **Query/response exchange is new on-chain storage, not a relay server.** A citizen posts a
      *blinded* query (safe to be public — that's what blinding is for) via a new extrinsic;
      committee members poll chain state for queries assigned to their slot (same pattern
      `pallet-courts` already uses for jury-duty selection — check whether you've been picked, rather
      than being reached out to); each responds with a second extrinsic. No push-notification
      dependency for correctness — an optional stateless push-reminder layer (watch chain events,
      trigger APNs/FCM) can be layered on later purely as a convenience, never required.
    - **Two distinct credentials per member device, doing two different jobs.** The member's
      existing chain account key signs the response transaction and is checked against an on-chain
      committee roster (*who* is allowed to answer for slot `i`); the OPRF secret share is what makes
      the response's cryptographic *content* correct. The Wasm module itself has no login of its own
      — it's a local library call inside whichever host app already has access to the securely-stored
      share, not a networked service with its own auth boundary.
    - **Founding-phase device handoff happens in person**, at the same event as the founding DKG
      ceremony each 7-person group already needs to hold live. This closes device distribution for
      the founding phase specifically; it does not extend to sortition scale (see "Still open").
    - **Tamper-resistance for the Raspberry Pi option needs an add-on TPM, not just disabling
      SSH.** Stock Raspberry Pi has no secure boot / hardware root of trust (the first-stage
      bootloader is closed-source and unverified), so a locked-down OS with no SSH still doesn't stop
      someone with physical access from pulling the SD card and reading it directly. Blocking
      remote/administrative access is still worth doing, but it's defense-in-depth on top of the
      12-of-35 threshold, not a substitute for it — no single device compromise (physical or remote)
      is supposed to matter beyond costing one share.
    - **Compensation, if any, stays treasury-funded** (unchanged from entry 73's own rejected-fee
      note) — reframed given there's no hosting bill in this model: compensation would be for member
      time/availability, not infrastructure cost.

    ## Rejected, on the record so they aren't re-proposed without the reason attached

    - **Reusing TACEO's live OPRF network for founding-phase committee operation** — same
      vendor-lock-in/permissioned-governance objection entry 73 already recorded; not reopened here.
    - **A centralized relay/queue server, specifically including a free-tier cloud Redis instance,**
      for the query/response exchange, and **splitting the data across several free-tier database
      providers** as a variant of the same idea. Neither distributes *trust* — if one party
      provisions and holds credentials for all the accounts (regardless of how many separate DBs the
      bytes live in), that party can reconstruct everything, which is the same structural mistake as
      "5 devices, no threshold" (see below). Managed free-tier databases are also third-party
      infrastructure dependencies with their own ToS/continuity risk, which the on-chain mailbox
      avoids by using infrastructure the project needs regardless.
    - **Lua (or any language without native arbitrary-precision field arithmetic) for the crypto
      core.** Would mean hand-rolling 254-bit modular arithmetic with no library support and no
      test vectors to check it against — exactly the class of risk this codebase has deliberately
      avoided elsewhere (Poseidon2 was ported from validated upstream source specifically to avoid
      this, see entry 75).
    - **A custom Redis module.** Managed free-tier Redis providers don't allow loading arbitrary
      native modules regardless of tier (multi-tenant security risk for the provider); even
      self-hosted, a module adds packaging complexity over just running the logic directly, for no
      benefit — Redis's data-structure features aren't doing anything for this workload.
    - **Fanning the secret-key computation out to blockchain validators/chain participants
      generally.** Structurally incompatible with how blockchains work: every validator re-executes
      every transaction to verify it, so anything computed on-chain is visible to the whole network
      by construction — the opposite of what a secret that must stay with one committee member
      needs. The general version of the idea (compute on shared infrastructure without that
      infrastructure seeing the secret) is a real field — MPC, TEEs, FHE — but none cleanly apply:
      routing the computation through many chain participants via MPC is functionally the
      "hierarchical composition of independent committees" idea entry 73 already found lacks sound
      published cryptography; TEEs swap the problem for trusting a hardware vendor's attestation
      infrastructure (with a real history of side-channel breaks); FHE is not computationally
      practical for this workload today.
    - **Collapsing a committee to a single device ("just 5 devices").** Would defeat the entire
      point of the 12-of-35 threshold structure — the security property is that compromising a
      committee requires colluding with or compromising 12+ independent people, not stealing one
      machine. A single device per committee reduces "compromise all 5 committees" from up to 60
      independent people down to 5 machines, plausibly within reach of one well-resourced actor.
      This is a distinct axis from "does a member need to actively do anything" (they don't — the
      computation is fully mechanical, no judgment call) — the 35 independent people exist for trust
      distribution, not to perform interesting work.
    - **The institutional/professional-operator hybrid** (drand/League-of-Entropy-style: vetted
      organizations run nodes, citizens retain accountability/oversight) — a real, credible
      alternative surfaced by research into how the most successful live precedent in this space
      (drand's League of Entropy, running in production for years) actually staffs its node-operator
      role: not by lottery among individuals, but by requiring prior experience operating critical
      infrastructure, filled by named institutions. Considered and **set aside for the founding
      phase**, not adopted: it's a bigger structural change than a hosting decision (it reopens who
      counts as "the committee" at all) and deserves its own dedicated adversarial review round the
      way entry 73's governance model got, rather than being folded in as a side effect of solving
      the hosting problem. Worth revisiting explicitly if the founding phase's citizen-hosted model
      turns out not to work in practice.

    ## Still open — not resolved by this entry

    - **The SLA window (~5-7 days) is a placeholder, not measured.** Reasoned from human-response-
      time being fundamentally slower than server-response-time and from the 12-of-35-per-committee
      × 5-committees compounding requirement, but carries the same caveat entry 73's original 48h
      figure already had: adjust once a real pilot produces real telemetry.
    - **Update/signing authority for locked-down devices.** balenaCloud answers *how* to push an
      update to a fleet of member-hosted devices; *who* is allowed to author one without becoming a
      new single point of compromise (a firmware-signing key that touches every device is a
      supply-chain target) is not designed.
    - **Device distribution logistics beyond the founding phase.** In-person handoff at the DKG
      ceremony works for 7 people; sortition-selected members at full committee scale, whose
      location isn't known in advance, need a real answer this entry doesn't provide — the closest
      real-world analogy floated (in-person pickup at a local civic office, the way passports/national
      ID cards are already collected) is unexplored past the analogy.
    - **DKG ceremony mechanics across heterogeneous member-owned devices** — everything above covers
      steady-state query answering, not the founding ceremony itself, which historically assumes
      synchronous participation on capable hardware. Whether it can run over the same on-chain
      mailbox with a longer coordination window, or needs a different one-time setup path, is
      unresolved.
    - **A governance trigger for voluntary/early rotation.** Only two rotation paths exist today:
      the scheduled 4-year cycle and Emergency Council + Courts' compromise-triggered rotation.
      Neither fits "move from phones to dedicated servers on our own schedule, nothing's wrong" —
      probably a `LegislatureOrigin`-gated call, matching the pattern already used elsewhere (e.g.
      `open_voting_epoch`), but not added.
    - **New on-chain primitives this design assumes are not implemented.** Confirmed by grep this
      session: `OprfCommitteeKeys` (the governance-approved key allowlist) already exists and is
      already checked in `register_citizen`/`reverify_citizen`/`migrate_oprf_scheme`, but
      `CommitteeMembers` (roster of which accounts belong to which committee slot),
      `committee_slot = H(date_of_birth) mod 5` assignment, and the query/response mailbox storage
      (`PendingOprfQueries`/`OprfResponses`) plus their two extrinsics do not exist anywhere in
      `pallet-identity` yet — this entry is architecture, not implementation.
    - **The OPRF committee service itself remains entirely unbuilt, unchanged by this entry** — same
      standing blocker entries 73-81 have named throughout. No production code changed this session;
      this entry is a design discussion, no circuits/runtime/mobile code was touched.
