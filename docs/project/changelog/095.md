# #095 — pallet-elections: wire the delegate-persona and backing-nullifier circuits (2026-08-23)

Closes the two "not done" items entries 093/094 flagged: `pallet-elections` now actually
consumes the delegate-persona proof (2e07f68) and the backing-nullifier proof (e31257a) instead
of trusting `ensure_signed`'s caller identity directly and tracking backing in plaintext.

## What changed

**`register_as_delegate`** is reshaped to accept `(persona_account, delegate_persona_id,
zk_proof, public_inputs, scheme_version, oprf_pk_hashes, display_name, profile_ipfs_hash)`.
`ensure_signed(origin) == persona_account` is required (front-running protection only holds if
the two are forced equal — the proof binds `persona_account`, not `who`). The outer proof is run
through `T::ZkVerifier::verify` (the real bb 5.0.0 pairing check — same verifier
`pallet_identity_zk::Config::ZkVerifier` uses, since a delegate-persona proof is cryptographically
just another outer ZKPassport proof), then `T::CommitteeKeyChecker::are_committee_keys_approved`
(new: without this, a prover could fabricate their own "committee" keys and self-mint unlimited
personas — the same gap `register_citizen` already guards against, applied here since 093/094
didn't need to address it yet), then `T::DelegatePersonaVerifier::check_delegate_persona`
(`runtime/src/anchor_verifier.rs`, from 2e07f68). A new `DelegatePersonaUsed: StorageMap<[u8;
32], ()>` nullifier map rejects a reused `delegate_persona_id`.

**`back_delegate`/`remove_backing`** now take `(delegate, zk_proof, public_inputs: [[u8; 32];
4])` instead of just `(delegate)`. A shared `verify_backing_proof` helper runs
`T::BackingProofVerifier::verify` (the real standalone UltraHonk pairing check from e31257a),
checks `root` via `T::BackingRootChecker::is_valid_backing_commitment_root`, checks the proof's
`delegate_persona_id` public input against `DelegatePersonaIdOf::get(delegate)`, and checks
`max_backings_per_citizen` against the live `MaxBackingsPerCitizen` value. The old plaintext
`BackingOf`/`CitizenBackingCount` maps are gone; a new `UsedBackingNullifier: StorageMap<[u8; 32]
nullifier, (AccountId submitter, [u8; 32] delegate_persona_id)>` replaces them — no on-chain
record of which citizen backs which delegate survives, only that some nullifier currently backs
a given persona. `run_election`'s aggregation logic itself is unchanged: `BackingCount` (delegate
→ `u32`) is still incrementally maintained, just now driven by nullifier insert/remove instead of
plaintext backer-set insert/remove.

**Two judgment calls made and documented, not left implicit:**

1. **`UsedBackingNullifier` stores `submitter`, not just `delegate_persona_id`** (the task's
   sketch was `StorageMap<nullifier, delegate_persona_id>`). Reasoning: the `backing-nullifier`
   circuit deliberately binds no `AccountId` (by its own design — see its module docs), so the
   exact `(zk_proof, public_inputs)` bytes a citizen submits to `back_delegate` are public call
   data afterward. Without recording and re-checking the submitter, *anyone* who observed those
   bytes on-chain could resubmit the identical proof to `remove_backing` and strip that citizen's
   backing without their consent — a genuine griefing vector the task's literal sketch would have
   left open. Requiring the same signer to reverse their own action closes it without leaking any
   privacy beyond what `back_delegate`'s own signer already publicly exposed.
2. **`back_delegate` no longer has a `CannotBackSelf` check.** The old check compared the tx
   signer against `delegate`, which was sound when the signer *was* the backing citizen. Under
   the nullifier scheme the tx signer is not cryptographically tied to the nullifier's underlying
   secret (a citizen could always have a cooperating relayer submit the tx), so the check would
   give false assurance without actually preventing anything. Removed and documented rather than
   kept as security theater; the residual exposure is bounded (a delegate can win at most one of
   the `BackingThreshold` backers they need this way, same as any single legitimate citizen).

**The backing cap (`MaxBackingsPerCitizen`) enforcement moved entirely into the circuit.** There
is no more on-chain per-citizen counter — the pallet can only check that a proof's claimed
`max_backings_per_citizen` public input matches live governance state
(`Error::MaxBackingsMismatch`); that a citizen cannot even construct a valid proof for a
`slot_index` beyond the real cap is a property of the circuit's own `assert_lt`, already covered
by that circuit's own test suite (094) and not re-provable at the pallet level without a mock
that would defeat the point. `Error::BackingLimitReached` is removed.

**Cross-pallet compatibility re-verified, not just assumed:** `persona_account` is an ordinary
`T::AccountId`, and `pallet_legislature::SeatLegislature`/`pallet_anticorruption::
DisclosureChecker` both operate generically over `T::AccountId` with no assumptions about how it
was derived — confirmed by reading both pallets' current code (pallet-anticorruption's 0529508
investigator-recusal change touches unrelated call paths, no conflict). No changes needed to
either pallet; the existing election-seating tests (which exercise both traits through the mock)
continue to pass unmodified in structure, just via updated proof-carrying helpers.

## Runtime wiring

New `runtime/src` trait impls: `Poseidon2AnchorVerifier` (anchor_verifier.rs) gains a fourth
trait impl, `pallet_elections::DelegatePersonaVerifier`, delegating to the same
`check_delegate_persona` free function. `BackingNullifierVerifier`
(backing_nullifier_verifier.rs) gains `pallet_elections::BackingProofVerifier`.
`ZkPassportUltraHonkVerifier` (verifier.rs) gains `pallet_elections::ZkProofVerifier`, identical
body to its existing `pallet_identity_zk::ZkProofVerifier` impl. `Runtime` gains
`AccountIdToBytes` (a real `AccountId32.into()` — not a placeholder, since this runtime's
`AccountId` genuinely is 32 raw bytes), `CommitteeKeyChecker` and `BackingRootChecker` (both
delegating to new/existing `pallet_identity_zk::Pallet` methods, real in both build modes since
they're storage lookups, not passthrough-able cryptography). `dev-mode` reuses the existing
`PassthroughZkVerifier`/`PassthroughAnchorVerifier` structs for the three genuinely-passthrough-
able Config items rather than inventing new stub types.

`pallet_identity_zk::Pallet` gained one new `pub fn`: `are_committee_keys_approved` — the
bool-returning half of the pallet's own private `check_committee_keys`, exposed so
pallet-elections can enforce the identical Sybil-resistance guarantee without duplicating
`OprfCommitteeKeys` storage access or depending on that pallet's `Error` type.

## What was NOT done

Same residual gaps 093/094/517e036 already documented, unchanged: submission-metadata
linkability (the signer/fee-payer/timestamp of the extrinsic itself, not the proof) still
survives — see the pallet's module doc comment. No real committee exists yet, so no real
delegate-persona or backing-nullifier proof has ever gone through this new pallet wiring
end-to-end (same standing limitation as registration itself).
