# #093 — Delegate-persona creation proof: circuit + Rust verifier (2026-08-22)

New feature, not a fix: a dedicated ZK proof for **delegate-persona creation** — the on-demand
event where a registered citizen chooses to become a delegate and registers a chosen
`persona_account` (AccountId) as their delegate identity. Deliberately a separate, fresh full
proof event, not folded into `register_citizen`/`reverify_citizen`. Circuit + Rust verifier
only in this pass; no pallet extrinsic calls the new verifier yet (see "Not done" below).

## What was built

- Three new domain separators in `circuits/oprf-identity-anchor/lib/identity-anchor/src/lib.nr`:
  `DS_DELEGATE_IDENTITY_INPUT`, `DS_DELEGATE_OUT`, `DS_DELEGATE` — mirroring
  `DS_IDENTITY_INPUT`/`DS_ANCHOR_OUT`/`DS_ANCHOR`'s roles exactly, for the delegate-persona
  flow. `derive_identity_input` was refactored into a shared `derive_scoped_identity_input(dg1,
  ds)` helper so the registration and delegate-persona derivations cannot drift apart; two thin
  `pub` wrappers (`derive_identity_input`, `derive_delegate_identity_input`) pick the separator.
  `derive_delegate_persona_term` mirrors `derive_committee_anchor_term`; `combine_committee_
  anchors` is reused unchanged (it only sums whatever 5 terms it's given).
- Two new circuits, mirroring `query`/`disclosure`'s round-1/round-2 split:
  - `delegate-query` (round 1) — structurally identical to `query`, blinds
    `derive_delegate_identity_input(dg1)` instead.
  - `delegate-persona` (round 2, disclosure-shaped/pipeline-integrated) — verifies 5 committees'
    responses to the delegate-scoped query, emits `delegate_persona_id`, and folds the citizen's
    chosen `persona_account` into `param_commitment` (`Poseidon2(202, delegate_persona_id,
    persona_account_lo, persona_account_hi, scheme_version, oprf_pk_hashes[0..5])`, tag `202`,
    distinct from registration's `200` and migration's `201`) so an observer cannot resubmit the
    proof paired with a different `persona_account` (front-running). Built directly in the
    disclosure-integrated shape, with no standalone `anchor`-style twin — the same "`comm_in` is
    an unauthenticated private witness of a standalone proof" argument that makes a bare `anchor`
    proof unsafe applies identically here.
- `runtime/src/anchor_verifier.rs`: `calculate_delegate_param_commitment`/`check_delegate_
  persona`, mirroring `calculate_param_commitment`/`check_registration_anchor`'s exact
  recompute-and-check pattern (same file, not a new sibling module — this is the same
  "recompute `param_commitment`, check it against the outer proof's already-verified
  `param_commitments[i]`" family as the other two). `account_to_field_limbs` reproduces the
  circuit's `pack_be_bytes_into_fields::<32, 2, 31>` split for a raw 32-byte AccountId in Rust,
  byte-for-byte. No pallet trait/extrinsic wiring — these are pure, storage-free functions ready
  for a future caller, same posture the module already documents for why the pairing check and
  the commitment recomputation are kept separate.

## The reuse-vs-fresh-OPRF-query design decision

The task spec flagged this as the one open design question requiring judgment, with a lean
toward "fresh/distinct scoping unless reuse is provably equally safe." Decision: **fresh/distinct
scoping** — delegate-persona creation runs its own two-round OPRF flow against a client input
scoped by `DS_DELEGATE_IDENTITY_INPUT`, a completely separate committee round-trip from
registration's, not a reuse of the citizen's cached `oprf_output_i` values under a new outer
combiner tag.

Reasoning: reuse (same `oprf_output_i`, only swap `DS_ANCHOR` for `DS_DELEGATE` in the outer
combiner) is *plausibly* safe under a bare random-oracle argument — the OPRF committee never
sees the outer domain separator at all (it's applied client-side, after unblinding, per
`TaceoLabs/oprf-nr`'s `generate_output`), so `anchor` and `delegate_persona_id` would be two
independent-looking Poseidon2 evaluations of a secret an on-chain observer never learns. But that
argument rests on exactly one thing holding: Poseidon2 providing genuine domain separation
between two hashes that share a secret preimage and differ only in one tag field. Fresh scoping
instead moves the reliance to the OPRF's own PRF security (a different client input means a
genuinely different, cryptographically independent per-committee evaluation) — the same class of
guarantee `DS_IDENTITY_INPUT` itself already depends on, not a new one. It also avoids a real
operational hazard the reuse design would introduce: the client would have to persist raw
per-committee `OPRFProof` material indefinitely after registration, which nothing else in this
pipeline requires (`disclosure`/`migrate-disclosure` both run fresh committee round-trips every
time), widening the at-rest secrets an attacker could exfiltrate from a compromised device. Since
delegate-persona creation is already specified as "a fresh, dedicated full proof event" requiring
its own passport scan, the extra committee round-trip is not incremental friction on top of that
— it is the event's natural cost, not an added one. Full reasoning is in `derive_delegate_
identity_input`'s doc comment (`circuits/oprf-identity-anchor/lib/identity-anchor/src/lib.nr`)
and the README's "Delegate-persona derivation" section.

  `delegate-persona`, same as `disclosure`/`migrate-disclosure`).

  DEV-ONLY 5-committee simulator, entries 078/081's own tooling) with a new

  in for the same real 5 committees answering a second, distinctly-scoped query, not an unrelated
  committee set — cross-checked by asserting committee 0's simulated public key matches between
  the two drivers' output (it does). `delegate_identity_input` for the fixture was obtained via a

  real `identity_anchor` lib. Result: `nargo execute` solved a genuine witness, `bb prove`/

  8-field layout `[comm_in, current_date, service_scope, service_subscope, param_commitment, 0,
  0, 0]`.

  `println` during verification, then removed from the circuit source), and the Rust function's

  `delegate_persona_id`, wrong `scheme_version`, mutated `pk_hash`, no matching commitment,

- `cargo check --workspace --exclude agora-node`: clean (only pre-existing, unrelated warnings).
- `cd oprf-committee-dev && cargo test`: 47/47 passing, unaffected by the new binary/module
  addition.

## What was NOT done (future phases build on this)

- **No pallet extrinsic calls `check_delegate_persona`.** This pass is circuit + Rust-verifier
  only, matching the task's scope. A future `pallet-elections`/`pallet-identity` extrinsic would
  need to: run `T::ZkVerifier::verify(zk_proof, public_inputs)` (exactly as `register_citizen`
  does), then `check_delegate_persona`, then record `(scheme_version, delegate_persona_id) ->
  persona_account` on-chain with a reused-`delegate_persona_id` rejection (mirroring
  `IdentityAnchorRegistry`'s `AnchorAlreadyUsed`).
- **No `circuit_registry_root`/VK-allowlist wiring was needed or added.** Checked first:
  `runtime/src/verifier.rs`'s `OUTER_CIRCUIT_VKS` allowlist is for the *outer* ZKPassport
  `main/outer/count_N` circuit variant, not for individual disclosure-subproof circuits —
  `disclosure`/`migrate-disclosure` were never added there either. A disclosure-shaped
  subproof's VK is recognized by being included in the off-chain-governed
  `circuit_registry_root` Merkle tree the outer circuit itself recursively verifies against,
  which is a governance action, not a runtime code change — same status `disclosure`/
  `migrate-disclosure` are already in.
- Same standing limitations every other round-2 circuit in this workspace has: no real OPRF
  committee exists, so `delegate-persona` has only been executed against the dev simulator;
  never run inside an actual outer ZKPassport proof; no independent cryptographic review.
