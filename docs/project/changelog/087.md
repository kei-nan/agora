# Changelog entry 087: on-device face match + liveness detection (Android)

Closes the gap `next-steps.md` item 12 and three places in `CLAUDE.md` flagged: `RegisterScreen.tsx`'s
registration flow used to hit `// TODO: await FaceMatch.verify(scan.faceImage);` and move straight to
`proving` with no liveness check and no comparison against the passport's photo. That TODO is now real
code — Android only, matching the existing NFC module's own scope (`ios/` still doesn't exist).

## Architecture decisions

**Camera capture: a custom CameraX-based native module, not `react-native-vision-camera`.**
Researched and confirmed this session: VisionCamera v4 is JSI-oriented and v5 (a Nitro rewrite, shipped
April 2026) requires React Native's New Architecture. This project has `newArchEnabled=false`
(`mobile/android/gradle.properties`), and `NfcPassportModule.kt` already documents deliberately avoiding
TurboModule/Codegen for exactly this old-bridge-compatibility reason. Rather than gamble on a
third-party bridge library's architecture story, `FaceCameraViewManager.kt` (a `SimpleViewManager` —
these predate Fabric, safe under the classic bridge) and `FaceCaptureModule.kt` (a classic
`ReactContextBaseJavaModule`) bind CameraX's `Preview`/`ImageCapture` use cases directly, mirroring
`NfcPassportModule.kt`'s exact shape — including its "companion object holds shared live state" pattern
(`activeInstance`/`onTagDiscovered` there, `activeImageCapture`/`bindImageCapture` here).

RN's own permission plumbing (`PermissionAwareActivity`/`PermissionListener`,
`com.facebook.react.modules.core`) *was* cross-checked against `react-android-0.74.0`'s real source this
session (downloaded via Maven Central): `ReactActivity implements PermissionAwareActivity` and already
forwards `onRequestPermissionsResult` to its delegate, so `FaceCaptureModule.requestCameraPermission`
works with zero `MainActivity.kt` changes.

**Face-embedding model weights: a specific, cited, real `.tflite` file, committed now.**
`mobile/android/app/src/main/assets/mobilefacenet.tflite` was fetched from `MCarlomagno/FaceRecognitionAuth`
on GitHub — confirmed via `gh api repos/MCarlomagno/FaceRecognitionAuth` to be **BSD-3-Clause**, blob sha
`057b98506a7fe9fb8ac8e64464bcacd6439084eb`, 5,233,552 bytes, source
`https://raw.githubusercontent.com/MCarlomagno/FaceRecognitionAuth/master/assets/mobilefacenet.tflite`.
**Provenance caveat, worth repeating everywhere this asset is touched (see `FaceMatchModule.kt`'s own doc
comment):** this traces back to `sirius-ai/MobileFaceNet_TF`, typically trained on MS1M/MS-Celeb-1M-derived
face data — a dataset Microsoft took down in 2019 over consent concerns. No face this codebase ever
*processes* is from that dataset (a citizen's registration photo/selfie never leaves their device), but
the model's own training-data lineage carries that history, which matters for a government identity
system. This was an explicit user decision (asked via a direct question this session), not a unilateral
call — the alternative considered was leaving the weights as a documented placeholder, same treatment
this codebase already gave "sourcing trusted DSC certificates" (`docs/project/next-steps.md` item 8,
log #63: flagged as "a governance/PKI problem, not a coding one").

**ML Kit variant: bundled (`com.google.mlkit:face-detection:16.1.7`), not Play-Services "unbundled".**
Keeps liveness detection fully on-device with no dynamic model download or Play Services dependency,
consistent with "nothing leaves your phone." ~6.9MB APK cost, accepted the same way this project already
accepts a much larger ZK proving-key footprint elsewhere.

**Liveness shape: 2-shot randomized challenge-response**, not continuous video analysis. A frontal
eyes-open baseline shot, then randomly either "blink" or "turn your head" — read via ML Kit's
`leftEyeOpenProbability`/`rightEyeOpenProbability`/`headEulerAngleY` (`RegisterScreen.tsx`'s
`baselinePassed`/`challengePassed`, thresholds flagged as unvalidated placeholders in the same file).
**Documented residual risk**: this is not anti-spoofing/depth-based — a prepared attacker with video of
the real person could plausibly defeat it. Deliberate scope boundary, same honesty pattern as the VRF
jury-randomness entry (`docs/project/next-steps.md` item 7) admitting its own residual grinding risk.

**DG2 JPEG2000 gap**: `BitmapFactory` cannot decode JPEG2000, which ICAO 9303 permits DG2 photos to use.
`FaceMatchModule.matchAgainstPassport` resolves `{matched: false, skipped: true, reason: ...}` rather
than throwing when `dg2MimeType` isn't `image/jpeg` — recorded (`RegistrationStatus.LivenessVerified`'s
`matchSkippedReason`), not silently dropped. Liveness-only still gates registration in that case. Same
honest-degrade pattern as the existing country-allowlist limitation.

## What was built

- **DG2 (face photo) reading** — `NfcPassportModule.kt` now also drains `EF.DG2` and parses it via
  JMRTD's `DG2File`/`FaceInfo`/`FaceImageInfo` (`org.jmrtd.lds.icao`/`org.jmrtd.lds.iso19794`) to get the
  raw JPEG/JP2 image bytes + MIME type — **this API genuinely was source-verified this session**: the
  real `jmrtd-0.8.6-sources.jar` (the exact version this project pins) was downloaded from Maven Central
  and inspected directly, confirming `DG2File(InputStream)`, `getFaceInfos(): List<FaceInfo>`,
  `FaceInfo.getFaceImageInfos(): List<FaceImageInfo>`, and `FaceImageInfo`'s (via `AbstractImageInfo`)
  `getMimeType()`/`getImageLength()`/`getImageInputStream()`, plus `ImageInfo.JPEG_MIME_TYPE`/
  `JPEG2000_MIME_TYPE` constants — not written from memory, unlike most of the rest of this entry.
  `mobile/src/native/nfcPassportReader.ts`'s `RawPassportData` gained `dg2`/`dg2MimeType`.
- **`mobile/android/app/src/main/java/com/agora/facematch/`** (new package): `FaceCameraViewManager.kt`,
  `FaceCaptureModule.kt`, `FaceMatchModule.kt`, `FaceMatchPackage.kt` — registered in `MainApplication.kt`
  alongside `NfcPassportPackage`/`KeystoreSigningPackage`.
- **Gradle**: CameraX (`camera-core`/`camera-camera2`/`camera-lifecycle`/`camera-view` 1.3.4), ML Kit
  face-detection 16.1.7, TensorFlow Lite 2.17.0 added to `mobile/android/app/build.gradle`.
  `AndroidManifest.xml` gained `CAMERA` permission + an optional (`required="false"`) camera feature
  declaration, same pattern as the existing optional NFC feature declaration.
- **`mobile/src/native/faceMatch.ts`** (new) — JS bridge to both native modules, mirroring
  `nfcPassportReader.ts`/`keystoreSigner.ts`'s pattern exactly (module-scope `NativeModules` capture,
  `isFaceMatchAvailable()` guard, base64 in/out). `mobile/src/native/FaceCameraView.tsx` (new) — thin
  `requireNativeComponent` wrapper for the live preview.
- **`mobile/src/chain/registrationState.ts`** gained a `LivenessVerified` pipeline stage between
  `PassportScanned` and `ProofMaterialAssembled`; `registrationReconciler.ts`'s pass-through stage list
  extended to match.
- **`RegisterScreen.tsx`** — the TODO is replaced with a real capture UI (`runLivenessGate`/
  `handleLivenessCapture`, rendered when `step === 'liveness' && livenessUi`): requests camera
  permission, shows `<FaceCameraView>` with challenge instructions, drives the 2-shot capture, calls
  `matchAgainstPassport`, writes `LivenessVerified` status, and gates progression to `proving` — a
  retryable failure like every other step in this screen's existing try/catch, not a hard stop.
- Tests: `mobile/src/native/faceMatch.test.ts` (new, 10 tests, mirrors `keystoreSigner.test.ts`'s
  `loadModule({linked, os})` mocking pattern — here, both `FaceCaptureModule` and `FaceMatchModule` must
  be linked for `isFaceMatchAvailable()`); `registrationState.test.ts`/`registrationReconciler.test.ts`
  extended to cover the new stage. `npm run type-check`: clean. `npm test`: 210/210 passing (15 suites,
  up from 197/14).

## What's still not verified

No Android SDK/JDK exists in this environment (confirmed in `CLAUDE.md`'s Current State) — none of the
new Kotlin has been compiled or run, same standing limitation `NfcPassportModule.kt` itself already
carries. Beyond the DG2 JMRTD API (genuinely source-verified, see above), the CameraX/ML Kit/TFLite calls
in this entry's four Kotlin files were written against documented, mainstream, stable public APIs but
were **not** independently re-verified against downloaded library source this session — treat them as
unverified until they actually compile. `MATCH_THRESHOLD` and the liveness-challenge thresholds
(`RegisterScreen.tsx`) are unvalidated placeholders with no real calibration corpus. `npm run lint` could
not be run to confirm this entry's style — this repo has no ESLint config file anywhere (`find . -iname
".eslintrc*" -o -iname "eslint.config.*"` returns nothing), a pre-existing gap unrelated to this change.
