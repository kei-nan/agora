# Completed next steps log — entry 87

87. **Wired up a real embedded smoldot light client for the desktop app**, replacing the
    hardcoded-RPC-only chain-read path for the nine commands the browsing pages actually call.
    CLAUDE.md's "Desktop App > Stack" section had flagged this as the intended long-term
    architecture since `smoldot`/`@polkadot/api` were first added to `desktop/package.json`,
    but — confirmed by grep before starting — there was zero smoldot usage anywhere in the
    actual code. That's no longer true for the JS side.

    ## Architecture decision: JS frontend, not the Rust backend

    Two plausible approaches existed: embed the `smoldot-light` Rust crate inside the Tauri
    backend and keep the `chain_*` Tauri-command surface unchanged internally, or move chain
    connectivity into the React frontend using `@polkadot/api`'s smoldot provider. Went with
    the latter, for reasons confirmed by reading the actual dependency graph rather than
    assumed:

    - `smoldot` and `@polkadot/api` were already **JS** dependencies in `desktop/package.json`
      (`smoldot@2.0.40`, `@polkadot/api@16.5.6`), not Rust ones — `smoldot-light` (the Rust
      crate) was never a dependency anywhere in this repo.
    - smoldot's primary, actively-maintained distribution is a JS/WASM npm package built for
      exactly this use case (a browser/webview-embedded light client driving `@polkadot/api`).
      Embedding it in a non-JS host process via `smoldot-light` is a real, valid pattern
      elsewhere, but it would have meant adding a Rust dependency nothing in this codebase had
      chosen, against a JS dependency the codebase already had chosen for the same job.
    - The frontend already has a clean seam for this: every page routes chain reads through a
      single `invoke()` wrapper (`desktop/src/lib/invoke.ts`) that already branches on
      Tauri-vs-browser-dev-mock. Adding a third branch — Tauri-but-route-to-the-light-client —
      for a fixed list of command names meant **zero changes to any page component**. An
      equivalent Rust-side swap would have required no frontend changes either, but would have
      meant embedding a second WASM runtime (smoldot's) inside the already-WASM-heavy Tauri
      binary for no benefit the JS path doesn't already have.

    ## What's real now

    - `desktop/src/chain/client.ts` — the light client itself. A small hand-written adapter
      (`ScShim`) satisfies the `@substrate/connect`-shaped interface `@polkadot/api`'s
      `ScProvider` expects (`{ WellKnownChain, createScClient }`), backed directly by the raw
      `smoldot` package's own API (`start()` / `client.addChain()` / the `jsonRpcResponses`
      async iterator) — `@substrate/connect` itself was never made a dependency; its interface
      is small enough to satisfy directly. Exposes `getApi()` (a singleton `ApiPromise`,
      connecting lazily on first call) and `onConnectionState()` (a
      connecting/syncing/ready/error observable — not currently wired into `ChainContext.tsx`,
      see "What's left" below).
    - `desktop/src/chain/queries.ts` — a straight TypeScript port of every SCALE byte-layout
      decode that used to live in `desktop/src-tauri/src/commands/chain.rs`
      (`chainStatus`, `fetchProposals`, `fetchLaws`, `fetchTreasury`, `fetchDepartmentBudgets`,
      `fetchRulings`, `fetchLegislatureData`, `fetchElectionsData`,
      `fetchAnticorruptionData`), reading through `api.rpc.state.getKeysPaged` /
      `queryStorageAt` / `getStorage` on the light-client-backed `ApiPromise` instead of
      `RpcClient`'s raw JSON-RPC over `reqwest`. Output shapes (field names, camelCase) are
      unchanged — pages didn't need to change.
    - `desktop/src/chain/scale.ts` — the hex/compact/u32/u128 decode helpers those queries
      need, a dependency-free port of the equivalent Rust helpers (no generated pallet types
      pulled in, same reasoning the Rust version had: these are read-only UI projections of a
      handful of fixed-width layouts, not consensus-critical decoding).
    - `desktop/src/lib/invoke.ts` — a `LIGHT_CLIENT_COMMANDS` map routes exactly those nine
      command names to the light client when running inside Tauri; everything else
      (`auth_generate_challenge`, `auth_poll_session`, `auth_start_callback_server`,
      `auth_verify_nullifier`, `chain_submit_extrinsic`, `fetch_ipfs_content`, `agent_ask`)
      still goes to the Tauri backend exactly as before. Browser-dev mode (`npm run dev`
      outside Tauri) is untouched — still serves `mocks.ts`, so working on the UI without a
      running chain still works.
    - `desktop/public/chainspecs/dev-chainspec-raw.json` — a checked-in
      `agora-node build-spec --dev --raw` snapshot (~2.1 MB, mostly the embedded runtime WASM
      in genesis storage) with `bootNodes` blanked to `[]`. `client.ts` patches that field in
      at connect time via one plain `system_localListenAddresses` JSON-RPC call to the local
      node, so the file doesn't need to hardcode a peer ID (which changes on every node
      restart unless `--node-key` is pinned). This is peer-discovery metadata, not a
      trust-sensitive read — smoldot independently verifies every subsequent state query
      against finalized GRANDPA consensus regardless of which peer told it where to dial, so
      this doesn't reopen the trust-boundary gap described below for
      `lookup_registered_account`.
    - `desktop/src-tauri/src/commands/chain.rs` gained a top-of-module architecture note and
      an update to the long trust-boundary comment on `lookup_registered_account` — that
      function's own doc comment used to say "zero smoldot usage anywhere in this Rust code
      today"; it now correctly says the light client exists (in JS) but this specific
      Rust-side lookup wasn't migrated to it, and explains concretely why (see "What's left,
      honestly" below).

    ## Proven working end-to-end against a real local chain — not just "it compiles"

    Built the real chain binary per this doc's own Critical Build Command
    (`WASM_BUILD_RUSTFLAGS="-C link-arg=--allow-undefined" cargo build --release`), ran it with
    `agora-node --dev --node-key <fixed> --listen-addr /ip4/0.0.0.0/tcp/30333/ws` (see "the
    `--listen-addr` requirement" below for why the flag is needed), built the real desktop
    frontend for production (`npm run build` — Vite's actual browser target, not a dev
    shortcut), served it, and drove it with a headless Chromium browser (Playwright) with
    `window.__TAURI_INTERNALS__` stubbed just enough to force `invoke.ts`'s Tauri branch (so
    the light-client path under test actually ran, instead of silently falling through to
    browser-dev mocks — an early version of this check gave a false pass for exactly that
    reason before the stub was added). Result: smoldot connected over the node's real libp2p
    `/ws` transport, downloaded and compiled the real ~1.0 MiB runtime WASM from chain, and the
    app's own `ChainStatusBar` component reached "Live" showing the chain's actual current
    block and finalized-block numbers (re-run twice against fresh nodes — most recently block
    #4/finalized #2 — not a one-off). This is real light-client sync against this specific
    runtime, not a generic smoldot demo.

    The other five migrated read pages (`/proposals`, `/laws`, `/legislature`, `/elections`,
    `/treasury`, `/anti-corruption`) were also driven headlessly and threw no runtime errors,
    rendering their correct empty states (this dev chain currently has no proposals, laws,
    treasury entries, etc. seeded — `--dev`'s genesis preset only seeds
    balances/aura/grandpa/sudo, per this doc's own "Critical Build Command" section) — but this
    check used full page reloads per route in quick succession, which is not how a user
    actually navigates a client-side-routed SPA, and one node process in this environment
    crashed mid-run from an apparently sandbox-specific `/tmp` cleanup racing its `--tmp` data
    directory (an environment artifact — confirmed by the node's own log citing a missing file
    under `/tmp/substrate*`, unrelated to this change) rather than anything in this change. The
    single clean `chain_status` run above is the one to trust as the real proof; the six-page
    run is corroborating, not primary, evidence.

    ## The `--listen-addr` requirement (a real, load-bearing gap, not a footnote)

    A plain `agora-node --dev --tmp` — this doc's own canonical "run the dev chain" command —
    does **not** open a WebSocket-capable libp2p listener by default; confirmed empirically:
    `system_localListenAddresses` against a vanilla `--dev --tmp` node returned only bare
    `/tcp/30333` multiaddrs, no `/ws` variant. A webview's smoldot instance can only dial
    WebSocket addresses (the same restriction any browser page has — no raw TCP sockets), so
    **the desktop app's light client cannot connect to a node started with just
    `agora-node --dev --tmp`** as this doc currently instructs elsewhere. Running the node with
    an explicit `--listen-addr /ip4/0.0.0.0/tcp/30333/ws` is a new, real prerequisite for
    desktop-app connectivity, called out in the "Desktop App > Stack" section above rather than
    silently assumed. `client.ts`'s `discoverWsBootnode` throws a specific, actionable error
    (naming the exact flag) rather than hanging or silently falling back to something fake when
    no `/ws` address is advertised.

    ## What's left, honestly

    - **`ChainContext.tsx` doesn't distinguish "connecting" from "syncing"** even though the
      light client's `onConnectionState()` observable in `client.ts` already reports that
      distinction internally — `ChainStatusBar`'s "Syncing..." label (present in the UI since
      before this change) stays unreachable; the light client's real, possibly-tens-of-seconds
      initial sync window shows as "Connecting to chain..." throughout instead. Cheap, not done
      here — genuinely deferred, not forgotten.
    - **The trust-boundary gap on `lookup_registered_account` (QR-auth's account lookup for
      signature verification) is not closed.** It still goes through the old plain-RPC path,
      unauthenticated against finalized consensus, exactly as before. Closing it would mean
      either a second, Rust-side light client just for this one call, or restructuring the
      auth flow so the already-connected JS light client performs the lookup and hands Rust a
      verified result to check the signature against — both are real protocol/architecture
      work this entry didn't attempt. See the updated doc comment on `lookup_registered_account`
      in `commands/chain.rs` for the concrete reasoning.
    - **`chain_submit_extrinsic` is unchanged** — still the same thin Rust passthrough to
      `author_submitExtrinsic` over the old `reqwest` RPC client, still not called from
      anywhere (per this doc's Authentication section, no phone-side flow produces the
      already-signed extrinsic it expects). Not migrated to the light client because nothing
      calls it yet either way.
    - **`fetch_ipfs_content` is unchanged** — a plain HTTPS gateway fetch, not a chain read, so
      out of scope for a light-client migration by definition.
    - **Production bundle size grew substantially**: the Vite production build is now
      ~4.2 MB / ~2.7 MB gzipped (previously well under 1 MB), almost entirely smoldot's own
      WASM bytecode plus `@polkadot/api`. Functionally fine, and expected for any
      light-client-embedding app, but no code-splitting (e.g. lazy-loading the chain module off
      the initial bundle) was attempted here — a real, cheap follow-up if desktop app startup
      time becomes a concern.
    - **The old Rust `reqwest` implementations of these nine commands were deliberately not
      deleted** — see the new top-of-module comment in `commands/chain.rs` for why (still the
      real implementation behind `auth_verify_nullifier`'s and `chain_submit_extrinsic`'s
      shared `RpcClient`/`rpc.rs`, and still covered by their own passing unit tests). They are
      simply no longer called by the frontend for these nine command names — genuinely dead
      code from the UI's perspective, kept as a tested reference/fallback rather than removed
      outright.
