# #092 — Persona-based multi-agent review + two security fixes (2026-08-20)

Not a `/project-review` pass — a user-requested review from three different angles, run as three
parallel read-only agents: an adversarial security researcher, an ordinary citizen/end-user
walking the actual product flows, and a product manager doing a launch-readiness/gap assessment.
Findings synthesized below, followed by the two fixes actually applied this session.

## Security researcher findings

1. **[FIXED, see below] Emergency re-declaration had no cooldown** — both
   `pallet-emergency-council` and `pallet-executive`'s independent emergency mechanism only
   guarded against a *second concurrent* emergency (`AlreadyActiveEmergency`); neither enforced
   any minimum gap between one emergency ending and the next being declared. The same
   supermajority that declares an emergency could redeclare a fresh one the block after the
   previous one ended, chaining into de-facto indefinite emergency powers despite
   `MaxEmergencyBlocks` capping each individual window. Severity: Medium-High (requires insider
   supermajority collusion, but that's exactly the threat model the sunset clause exists to
   defend against).
2. **court-oracle prompt-injection delimiter doesn't escape its own closing tag**
   (`court-oracle/src/context.rs:27`, `wrap_untrusted_content`). A law author can embed the
   literal string `</untrusted_external_content>` followed by fake directives to break out of
   the delimiter — mechanical, not skilled prompt engineering. Mitigated in part by the M-of-7
   `OracleMembers` approval council, but not eliminated (multiple oracle instances reading the
   same poisoned content could each be misled). Severity: Medium. Not fixed this session — needs
   escaping/stripping of the delimiter string from untrusted content before wrapping.
3. **[FIXED, see below] `remove_oracle_member` didn't purge a removed member's already-cast
   approvals** from in-flight `PendingOracleProposal`s in `pallet-courts`. Severity: Medium.
4. Delegation-cap check in `pallet-voting` has a narrow staleness gap around `total_citizens()`
   shrinking via revocations between edge creation and re-evaluation — only ever too-permissive,
   never lets a specific enqueued edge bypass its own check. Severity: Low/informational, not
   fixed.
5. Checked and found sound: oracle approval majority math (`OracleApprovalNumerator/Denominator`
   is correctly strict, not off-by-one), `DisclosureChecker` fallthrough logic, identity
   nullifier registration/revocation ordering, overflow handling (`saturating_*` throughout), no
   stray `unwrap()`/`expect()` in dispatchable call bodies.

## Citizen/UX findings (not fixed this session — product work, not a security fix)

- Mobile shows raw hex (`topicHash`) instead of proposal/law/petition content — mobile never
  fetches IPFS content anywhere, unlike desktop. Biggest usability gap: undermines informed
  voting.
- `RegisterScreen.tsx` deliberately throws post-scan (no proving keys yet) — no citizen can
  register today; honestly messaged, but blocks the whole product.
- Filing a `CitizenConduct` case requires pasting a raw 32-byte hex nullifier by hand.
- No proactive notice of being a party to a case or of a closing appeal window.
- `SeatingSkippedNoDisclosure` (delegate skipped for lapsed disclosure) is emitted on-chain but
  never surfaced in either app.
- No country-allowlist messaging before/during registration.
- Oracle council composition/approval count is invisible to citizens viewing a ruling.

## Product manager findings (not fixed this session — process/roadmap, not code)

- OPRF committee is the right critical-path call, but committee-*formation logistics* (recruiting
  and provisioning ~175 real people across 5 committees) is the actual long pole, and has no
  owner or timeline anywhere despite being flagged as unsolved in nearly every OPRF-related log
  entry.
- Two independent emergency mechanisms (this entry's fix reduces, but doesn't eliminate, the risk
  this creates — see below).
- Live Claude API key for court-oracle is trivially unblockable but bundled in docs with the
  much-harder OPRF blocker, overstating its difficulty.
- Mobile-native-build is blocked only by this *sandbox* lacking JDK/SDK, not architecturally —
  conflating it with OPRF-scale blockers distorts prioritization.
- No pilot-onboarding, compliance, incident-response, or key-ceremony documentation exists
  anywhere; a government partner has no way to audit the system without reading raw Substrate
  storage.

## Fixes applied this session

**1. Post-emergency cooldown** (`pallets/pallet-emergency-council/src/lib.rs`,
`pallets/pallet-executive/src/lib.rs`). Added `EmergencyCooldownBlocks: Get<u32>` to both
pallets' `Config`, a new `CooldownUntil<T>` storage item set to `now + EmergencyCooldownBlocks`
on every path that ends an emergency (sunset expiry and early `vote_end_emergency` in
`pallet-emergency-council`; lapse, sunset expiry, and early `vote_end_emergency` in
`pallet-executive`), and a check in `vote_declare_emergency` that rejects
(`EmergencyCooldownActive`) while `now < CooldownUntil`. Wired to `7 * DAYS` (50,400 blocks) in
`runtime/src/configs/mod.rs` for both pallets. 7 new tests across the two pallets' `tests.rs`
covering cooldown-after-expiry, cooldown-after-lapse (executive only), cooldown-after-early-lift,
and successful redeclaration once the cooldown elapses; one pre-existing test
(`emergency_auto_expiry_clears_vote_maps_and_pending_proposal`) updated to advance past the new
cooldown before its redeclare step. `cargo test -p pallet-emergency-council -p pallet-executive`:
132/132 passing. `cargo check -p agora-runtime --features dev-mode`: clean.

This does not eliminate the redundancy the PM review flagged (two independent emergency
mechanisms, no documented rule for which a real crisis should invoke) — it closes the specific
re-declaration-chaining hole in each mechanism individually.

**2. Oracle-approval purge on member removal** (`pallets/pallet-courts/src/lib.rs`).
`remove_oracle_member` now also walks `OracleApprovals` (via `StorageMap::translate`) and strips
the removed account from every in-flight proposal's approval list, not just from `OracleMembers`.
Previously a compromised-and-removed member's already-cast approval kept counting toward quorum
on any proposal they'd approved — meaning the intended incident-response path ("member's key is
compromised, root removes them") didn't actually shrink the approvals a malicious
submission/finalization needed. New test
`remove_oracle_member_purges_stale_approval_from_in_flight_proposal` reconstructs the exact
scenario (3-member council, proposer approved, proposer removed, verify the remaining 2-member
council genuinely needs 2 fresh approvals, not 1 fresh + 1 stale). `cargo test -p pallet-courts`:
45/45 passing.
