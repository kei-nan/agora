    production bug found and fixed as a side effect.** Four pieces of work were built

    ## What was built and verified

    - **`pallets/pallet-identity`: the on-chain query/response mailbox is real.**
      `CommitteeMembers` (roster per committee slot, governance-gated add/remove
      mirroring `OprfCommitteeKeys`'s existing pattern), `committee_slot_for(date_of_birth)
      -> u8` (Poseidon2 mod 5, reusing `pallets/poseidon2-bn254` rather than
      reimplementing it), `PendingOprfQueries`/`NextQueryId`/`OprfResponses`, and two new
      extrinsics — `submit_oprf_query` (call index 15) and `submit_oprf_response` (call
      index 16, checks slot membership, expiry, and idempotency). `dlog_proof` is bounded
      to exactly 64 bytes (`BoundedVec<u8, ConstU32<64>>`) — independently confirmed
      against the real Wasm core's proof size (see below) rather than guessed. 90/90
      pallet-identity tests pass (37 new), re-run and confirmed after merging into the
      main tree, not just taken from the building agent's own report.
    - **`oprf-committee-dev`: the crypto core now has a real `wasm32-unknown-unknown`
      build.** A new `src/ffi.rs` wraps `oprf::evaluate` (the actual "what a committee
      member's node does" function — untouched, no cryptographic logic modified) behind
      a C-ABI (`oprf_alloc`/`oprf_evaluate_query`/`oprf_dealloc`), fixed 160-byte input
      (`sk || b_q.x || b_q.y || ds_dlog || seed`), fixed 192-byte output (`pk || dlog_e/
      dlog_s || response_blinded`). A `rand`-feature fix (drop `"std"`, keep only
      `"std_rng"`) was needed to compile for wasm32 at all — `getrandom` otherwise hard-
      errors on bare `wasm32-unknown-unknown`; verified this didn't remove anything the
      crate actually used (no `OsRng`/`thread_rng()` anywhere). A wasm-vs-native
      equivalence test (loads the compiled `.wasm` via `wasmi`, asserts byte-identical
      output to the native call on the same fixture) is the actual proof this is the same
      already-validated math, not a second implementation to trust separately. 33 lib
      tests + 1 equivalence test pass; independently rebuilt and re-run in the main tree
      (241KB artifact, confirmed present at
      `oprf-committee-dev/target/wasm32-unknown-unknown/release/oprf_committee_dev.wasm`).
    - **`committee/`: a new, separate mobile app/module** (sibling to `mobile/`/`desktop/`,
      deliberately not sharing `mobile/`'s dependency graph, per entry 82's isolation
      rationale) for the poll-for-duties/fulfill-duty flow, with dev-only key storage
      mirroring `identity.ts`'s existing wallet-key pattern and an injectable
      `CommitteeCrypto` boundary (still a throwing stub — an RN-side Wasm runtime to
      actually load the module above is genuinely separate work, not attempted here).
    - **`committee-node/`: a new Rust crate + Dockerfile** for laptop/Pi deployment — a
      real hand-rolled JSON-RPC client mirroring `desktop/src-tauri/src/rpc.rs`'s
      approach, real sr25519-signed extrinsic construction pinned to the runtime's own
      `sp-core` version, real `wasmtime` module loading, real `age`-encrypted key-file
      decryption, `age`-encrypted key storage explicitly flagged as a placeholder (not
      real hardware-backed custody — that's still unsolved, per entry 82's own open
      items).

    ## Reconciliation — where the two guessing agents' assumptions landed

    `committee/` and `committee-node/` were built concurrently with the pallet and Wasm
    work, against a provisional interface spec, explicitly told to flag assumptions for
    reconciliation. After merging, every flagged assumption was checked against the real
    thing, not assumed correct:

    - **Storage/call names, hasher, field layout, and the `dlog_proof` byte bound**: all
      confirmed correct as guessed (`Blake2_128Concat`, the 64-byte x-then-y
      `blinded_query` layout, 64-byte `dlog_proof`) — the pallet-identity and Wasm-core
      agents had independently checked the same real details (each other's outputs)
      without coordinating, and they agreed.
    - **`submit_oprf_response`'s call index**: guessed 13, actually **16**
      (`submit_oprf_query` is 15) — both `committee-node/src/config.rs`'s default and
      doc comment corrected.
    - **`OprfResponses`' shape**: guessed as "list of accounts who responded" (per-address
      lookup); the real pallet is a `StorageDoubleMap<(query_id, committee_slot)>` holding
      *one* optional record — a presence check per pair, not a per-address search, since
      any one member of a slot's roster answering closes the duty for the whole slot.
      `committee/src/chain/oprfCommittee.ts`'s `hasAlreadyResponded` was wrong in a way
      that would have kept re-offering "pending" duties another roster member had already
      fulfilled — fixed to a plain presence check, its test suite updated to match.
    - **The Wasm ABI**: both agents' guesses (`evaluate_query(sk, x, y) -> (x, y,
      proof)`) were missing two real inputs entirely — `ds_dlog` (a public domain-
      separator constant) and `seed` (fresh per-call CSPRNG randomness the wasm module
      cannot source itself on `wasm32-unknown-unknown`, or it leaks the secret key via
      nonce reuse). Both hosts were rewritten against the real ABI: `committee-node`'s
      `wasm_host.rs` now sources `seed` from `OsRng` and hardcodes the real `DS_DLOG`
      constant (`circuits/oprf-identity-anchor/lib/identity-anchor/src/lib.nr`'s
      `1523098184080632582082867317389990410064981862`, independently re-derived from
      decimal to bytes and cross-checked, not copied blind); a new test loads the
      *actual* compiled `.wasm` artifact and confirms the real module's own
      `ERR_ZERO_SECRET_KEY` comes back through the reconciled marshaling — not a fixture,
      the real thing. `committee/`'s `CommitteeCrypto` interface was simplified to match
      (one 64-byte `blindedQuery` param, `ds_dlog`/`seed` treated as implementation
      details no caller should manage) — still a throwing stub pending an RN Wasm
      runtime, but the *shape* it'll need to satisfy is now correct.

    ## A real bug found and fixed, unrelated to the OPRF work itself

    While porting `desktop/src-tauri/src/rpc.rs`'s `twox128_hex` for `committee-node`'s
    own RPC client, a known-answer check against `twox128("System") ==
    "26aa394eea5630e07c48ae0c9558cef7"` (a standard reference value across the Substrate
    ecosystem) failed against the desktop app's existing formula. `format!("{:016x}",
    r0.to_le())` doesn't do what it looks like it does: `u64::to_le()` is a no-op on any
    little-endian host, and `{:016x}` prints a value's ordinary (big-endian) hex digits
    regardless — neither step produces the little-endian *byte sequence* TwoX-128
    actually needs. Confirmed empirically (a standalone repro produced
    `e03056ea4e39aa26f7ce58950cae487c`, not the known-good value) before touching
    anything. **Fixed in `desktop/src-tauri/src/rpc.rs` directly** (`to_le_bytes()`,
    hex-encoded byte-by-byte) with a regression test against the same known vector.
    `storage_prefix()` — used by every real chain read the desktop app makes
    (`fetch_proposals`/`fetch_laws`/`fetch_treasury`/`fetch_rulings`, the QR-auth
    nullifier check, courts, elections, anti-corruption) — was very likely computing
    wrong storage keys on every real (little-endian) deployment, silently returning
    empty results rather than erroring. This directly contradicts
    `docs/project/apps/desktop.md`'s claim that these commands "read from real chain
    storage" — worth a closer look at whether that was ever actually exercised against a
    live chain, separate from this entry.
