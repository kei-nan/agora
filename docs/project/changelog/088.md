    ## The actual risk being designed against

    A single key (or account) that alone can push new code to every founding-phase member's
    device is a strictly worse single point of failure than the OPRF secret-sharing scheme it
    would be updating. Compromising one committee member's share costs an attacker one of
    12-of-35 (or 6-of-7 at founding scale); compromising the one key that signs fleet updates
    costs an attacker the entire fleet in one step, with no threshold to clear at all. Any answer
    that reduces to "the project's balenaCloud account" or "one maintainer's signing key" recreates
    exactly the centralization the whole 5-independent-committee governance model (entry 73) and
    citizen-hosted-device model (entry 82) exist to avoid — this entry is intentionally suspicious
    of any answer shaped that way, on principle, not just for this one supply-chain detail.

    ## Decided

    Split the problem into two questions that a single mechanism should never answer together:
    **who says a given build is safe** (authorization) and **how bytes physically reach a
    device** (distribution). balenaCloud (or whatever fleet tool is actually live) only ever
    fills the second role.

    - **Reproducible builds, required.** The build pipeline (`committee/scripts/build-wasm-core.sh`
      for the mobile Wasm core, `committee-node/Dockerfile` for the laptop/Pi image) must produce
      byte-identical output from a pinned source commit and a pinned toolchain version.
      Deterministic Rust/Wasm builds are ordinary, well-supported engineering practice, not new
      infrastructure — this project already compiles one portable `oprf-committee-dev` Wasm core
      specifically so the sensitive cryptography is validated once (entry 82); reproducibility is
      an incremental requirement on that same pipeline, not a new one. The payoff: any committee
      member, or any outside auditor, can independently rebuild from the public source at a named
      commit and confirm the resulting hash matches what's being distributed, without trusting
      whoever operates the fleet dashboard.
    - **A small, cross-committee update-review sub-quorum attests on-chain to a build hash before
      any device is allowed to trust it — not the full cryptographic threshold, and not one
      person.** Concretely: one designated technically-capable reviewer from *each* of the 5
      independent committees (entry 73's topology), attesting on-chain that they've checked a
      specific build hash against the published source. Reusing the on-chain
      poll-and-attest mailbox pattern entry 82 already established for query/response — no new
      infrastructure class, just a new record type — a fleet tool only ever distributes a hash
      that has cleared this on-chain bar. This deliberately spans all 5 committees (mirroring
      entry 73's own cross-committee-independence principle) so that no single committee's
      compromise, on its own, can bless a malicious build; and it is deliberately a *different,
      much smaller* group than the 12-of-35 cryptographic threshold, because asking that many
      people to review a software release for every routine patch is operationally unworkable and
      conflates two unrelated questions ("who can jointly evaluate the OPRF function" vs. "who
      authorizes new code to run on the machines that hold the shares").
    - **Distribution stays separate and replaceable.** Whoever operates the balenaCloud fleet (or
      equivalent) only ever pushes a hash the on-chain quorum already attested to; that operator
      role can rotate, be audited, or be swapped for a different tool entirely without touching
      the trust question at all, because it was never the thing deciding what's safe.

    ## Rejected, on the record so they aren't re-proposed without the reason attached

    - **A single project-controlled signing key** (balenaCloud's own default model). This is the
      exact failure mode this entry exists to avoid — see "The actual risk being designed
      against" above.
    - **Self-attestation by the receiving device's own member** ("I clicked accept"). Verifies
      consent, not safety — a member has no realistic way to audit a compiled Wasm/container
      image themselves, so on its own this reduces to "trust whoever built it," without even the
      independent-rebuild check reproducibility provides.
    - **Reproducible builds with no authorization gate at all.** Reproducibility only proves "this
      hash matches this published source" — it says nothing about whether that source is safe. A
      malicious change is exactly as reproducible as a benign one; some human trust decision is
      still required on top, which is what the update-review sub-quorum provides.
    - **Requiring the full 12-of-35 (or 6-of-7 founding) cryptographic threshold to also attest to
      every software update.** Conflates the crypto-evaluation threshold with a code-review
      quorum — two different competencies and two different operational cadences (query answering
      is routine and mechanical; a security patch needs to ship faster than a full-committee poll
      realistically allows).
