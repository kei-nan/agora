    ## What was built and verified

    - **A real, working Rust binary crate**, its own Cargo workspace root at repo root (sibling
      to `oprf-committee-dev/`, same "don't pull `agora-runtime`'s WASM-builder build graph into
      an unrelated component" reasoning that crate's own `Cargo.toml` already documents).
      `cargo build`/`cargo test` both succeed in this environment: 34 tests passing, zero
      warnings.
    - **A real hand-rolled JSON-RPC chain client** (`src/rpc.rs`), ported from
      `desktop/src-tauri/src/rpc.rs`'s approach with the write-side additions a read-only app
      never needed (`state_getRuntimeVersion`, `chain_getBlockHash`, `system_accountNextIndex`,
      `author_submitExtrinsic`). **A real, independently-found bug in the desktop app's copy**:
      a known-answer check against `twox128("System") == "26aa394eea5630e07c48ae0c9558cef7"` (a
      standard Substrate reference vector) fails against `desktop/src-tauri/src/rpc.rs`'s
      `format!("{:016x}{:016x}", r0.to_le(), r1.to_le())` in this tree — `u64::to_le()` is a
      no-op on any little-endian host for the numeric value, and `{:016x}` prints ordinary
      big-endian hex digits regardless, so neither step produces the little-endian byte sequence
      TwoX-128 needs. This crate's own `twox128_hex` (`to_le_bytes()` + byte-by-byte hex,
      verified against the same vector) is correct; fixing the desktop app's copy is left
      untouched as out of this task's scope, but every desktop RPC command that reads chain
      storage depends on that broken function, so this is worth a dedicated fix.
    - **A real hand-encoded, sr25519-signed `UncheckedExtrinsic`** (`src/extrinsic.rs`), pinned
      to the same `sp-core` 36.1.0 the runtime uses, transcribing `runtime/src/lib.rs`'s
      `TxExtension` tuple and `pallet-courts`' real `submit_ai_ruling` call index (1) and
      argument shape — read from the pallet source, not guessed.
    - **Case-context building for all four `CaseSubject` variants** (`src/context.rs`, pure,
      unit-tested): `LawChallenge` fetches `Constitution::Laws` and best-effort fetches the
      law's full text from the public IPFS gateway (mirroring `desktop`'s own
      `fetch_ipfs_content` convention); `TreasuryDispute` fetches `DepartmentBudgets`/
      `DepartmentSpent`/`FrozenDepartments` directly and scans `ExpenditureLog`/`PalletAudit`'s
      `AuditLog` for entries tagged with the department (documented as a real, non-scaling
      approach — those logs aren't department-indexed on-chain); `General`/`CitizenConduct`
      honestly report that no further on-chain context exists for those subjects rather than
      inventing fields pallet-courts doesn't have.
    - **A real Claude API request/response layer** (`src/claude.rs`), reusing
      `desktop/src-tauri/src/commands/agent.rs`'s request shape but with a fresh system prompt
      making explicit that this call produces a binding on-chain ruling (per `/CLAUDE.md`'s
      court-system design), not a read-only citizen chat answer, and requiring the model to cite
      specific on-chain context and to explicitly flag insufficient context rather than
      speculate. Model defaults to `claude-opus-5` (not the desktop app's `claude-sonnet-4-6`) —
      a deliberate choice given this call's correctness stakes, not a copy-paste. Response
      parsing (`VERDICT:`/`REASONING:` sections) and a `stop_reason: "refusal"` guard (this
      service refuses to invent a ruling when Claude's safety classifiers decline, rather than
      submitting something on-chain regardless) are unit-tested against literal fixtures,
      including one shaped like a real Anthropic Messages API response.
    - **A new IPFS publishing client** (`src/ipfs.rs`) — confirmed by grep that none existed
      anywhere in this codebase before this entry; every existing consumer only reads content by
      an already-known hash. Implemented against a local Kubo-compatible daemon's HTTP API
      (`POST /api/v0/add`, `127.0.0.1:5001` default) — evaluating alternatives (e.g. a hosted
      pinning service) was out of scope for the time available, noted plainly rather than
      silently decided. **A real mismatch found and resolved by explicit choice, not paper over**:
      `submit_ai_ruling`'s doc comment calls `ruling_hash` an IPFS CID, but every existing reader
      (`desktop`'s `hash_to_cid`) treats the on-chain 32-byte value as a raw SHA-256 digest of
      content stored as a bare block — which a standard `ipfs add` does not produce (it wraps
      content in UnixFS/`dag-pb` even for one small file). This crate submits the digest bytes
      actually inside the CID `ipfs add` returns, keeping `desktop`'s existing
      `fetch_ipfs_content` reconstruction working, at the documented cost that `ruling_hash`
      cannot be verified by hashing the plaintext document directly — see `ipfs.rs`'s header
      comment.

    ## A real gap found while building this, not fixed (flagged, not silently worked around)

    Reading `pallets/pallet-courts/src/lib.rs` closely surfaced something the task's own framing
    didn't anticipate: `submit_ai_ruling` alone never enforces anything. It only records
    `ruling_hash` and starts the 7-day appeal clock (`AIRulingBlock`). The actual verdict that
    drives auto-enforcement (pause a law, freeze a department, suspend a citizen) is set only by
    `auto_finalize`, reachable either via `cast_jury_vote` (the appeal path) or via
    `finalize_ruling(case_id, verdict)` — a **separate**, oracle-signed call requiring the same
    verdict as an explicit argument, callable only after the appeal window closes unappealed.
    `court-oracle` does not make that second call — the task explicitly scoped
    verdict/enforcement out, on the premise that it happens automatically once
    `submit_ai_ruling` lands. That premise doesn't hold; see `court-oracle/README.md`'s "A real
    gap found" section for the full accounting. This is a real, concrete piece of remaining work
    (scheduling/calling `finalize_ruling` after each case's appeal window closes), not merely a
    deferred nice-to-have.
