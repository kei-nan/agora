    - **`-t evm`, not the default `ultra_honk` scheme, and why it matters.** `bb write_vk` without a target flag emits a poseidon2-transcript VK meant for recursive (in-circuit) verification — different hash function, different size in general. `verifier.rs`'s module docs are explicit that the outer proof is the one variant verified on-chain and is proved/keyed with `-t evm` (keccak transcript), so that's the flag that had to be used here. Generated both once to confirm the difference is real: the default-scheme VK for this same circuit is also 3680 bytes (matching log #69's `query`-circuit VK size, an unrelated coincidence of both being small-transcript UltraHonk VKs), while the `-t evm` VK is 1888 bytes — confirming the two schemes are genuinely different artifacts, not just differently-flagged output of the same computation.
    - **This does not unblock verification.** `lookup_vk(4)` now returns `Some(vk)` instead of `None`, but `verify_inner` still calls `ultrahonk::verify`, which is an intentional stub returning `None` unconditionally (log #70's fail-closed posture, unchanged). A real proof for `count_4` is now rejected for the correct reason — "no pairing backend" — rather than the previous, less informative "no VK installed." Nothing else in the accept/reject behavior changed.
    - **Test fixed, not just left broken.** `verifier::tests::rejects_an_uninstalled_verification_key` asserted `lookup_vk(4).is_none()` — written deliberately, per its own comment, to fail exactly when this happened ("If this test starts failing, the asset was populated — which is good news").
