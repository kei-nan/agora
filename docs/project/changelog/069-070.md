The three that consume an OPRF committee response cannot be executed at all until a committee service exists (explicitly out of scope, see below), so this is PARTIAL, not DONE.     - **Correction to log #67: the fork does not need to reach into `dsc-to-id/src/lib.nr` at all.** Log #67's "explicitly open (now RESOLVED)" bullet traced the blocker to `dsc-to-id/src/lib.nr:29`'s `calculate_private_nullifier(dg1, e_content, sod_signature)` call and concluded that repurposing `oprf-auth` meant forking that circuit, regenerating its verification key, and re-registering it in `circuit_registry_root` — "a fork with a new trust-audit surface, not a call-site parameter swap." Reading the commitment function itself rather than just its call site shows that isn't required: `hash_salt_dg1_dg2_hash_private_nullifier` (`src/noir/lib/commitment/common/src/lib.nr:242`) — the commitment `oprf-auth` already checks — commits over `salted_dg1.get_hash()` **as well as** the private nullifier. DG1 is therefore already bound into the exact commitment the OPRF circuit consumes, and the personal-number field is nothing but a byte range of DG1. The substitution happens entirely inside the forked leaf circuit, reading different bytes out of a value that was already authenticated by the SOD signature check the pipeline performs anyway. Net effect: `csc-to-dsc`, `dsc-to-id` and `integrity` are untouched, their VKs and existing circuit-registry entries stay valid, and exactly one upstream file is genuinely forked (`src/noir/bin/oprf-auth/src/main.nr` → `circuits/oprf-identity-anchor/query/src/main.nr`). Log #67's conclusion that this is real circuit engineering rather than a parameter swap still holds; its estimate of the *blast radius* was too large.
    - **What was built.** `circuits/oprf-identity-anchor/` is a four-binary Noir workspace plus one shared library, because the OPRF protocol is inherently two-round (blind → committee evaluates → unblind) and no single circuit can cover it. Measured with `nargo info`, cross-checked against `bb gates`: `query` (6,733 ACIR opcodes / 12,113 bb circuit size) is the actual fork of `oprf-auth` and blinds the identity input; `anchor` (44,462 / 60,168) verifies the committee's response and emits the anchor standalone; `disclosure` (46,423 / 63,473) does the same but shaped as an outer-circuit disclosure subproof and adds an expiry check; `migrate` (87,715 / 115,113) evaluates under two committee generations for log #67's 4-year scheme rotation. `lib/identity-anchor` holds the derivation shared by all four so the value `query` blinds and the value `anchor` verifies cannot drift apart — a correctness requirement, since a one-byte disagreement would simply fail OPRF verification with no useful diagnostic.
    - **The fork costs +89 ACIR opcodes.** Compiled unmodified upstream `oprf-auth` first, on the same toolchain, precisely to have a baseline: **6,644** opcodes. The forked `query` is **6,733**. That 89-opcode delta is the entire personal-number slice, the populated check, the issuing-country binding and the clear-value assertions. Recorded because it's the kind of number that's easy to assume and cheap to actually measure.
    - **Derivation, concretely.** `personal_number = DG1[77..91]` (flat MRZ 72..86, i.e. ICAO Doc 9303 Part 4 TD3 line 2 character positions 29–42 — log #67's figure, re-derived here rather than taken on trust and cross-checked against ZKPassport's own already-verified TD3 offsets in `utils/src/constants.nr`, which put the document number at 44, nationality at 54, birthdate at 57, gender at 64 and expiry at 65; the personal number is the 14 characters after the expiry check digit at 71, before its own check digit at 86 and the composite check digit at 87). Then `identity_input = Poseidon2(DS_IDENTITY_INPUT, pack_be(personal_number[14]), pack_be(issuing_country[3]))`, `oprf_output = verified_oprf(..., identity_input, DS_DLOG, DS_ANCHOR_OUT)`, `anchor = Poseidon2(DS_ANCHOR, oprf_output, scheme_version)`. Issuing country is folded in even though the one-chain-per-country deployment model makes it constant — it costs one Poseidon2 input and keeps the anchor space collision-free by construction if the allowlist ever widens. Domain separators follow ZKPassport's own convention of an ASCII string read as a big-endian integer (confirmed by decoding theirs: `DS_OPRF = 1330664006` is `b"OPRF"`, `DS_DLOG` is `b"DLOG Equality Proof"`).
    - **`DS_DLOG` is deliberately *not* an Agora-specific value.** Unlike the other three domain separators, this one has to match the deployed committee service's own configuration, because the service is what produces the Chaum-Pedersen proof it separates. Kept byte-identical to ZKPassport's, which is the value TACEO's `oprf-service` is already known to be driven with. The other three (`DS_IDENTITY_INPUT`, `DS_ANCHOR`, `DS_ANCHOR_OUT`) are client-side only and are Agora-specific.
    - **Three asserts added for non-obvious reasons, each with a real failure mode behind it.** (1) *TD1 ID cards rejected outright* — their MRZ has a different layout, so reading TD3 offsets out of one produces a well-formed but meaningless anchor; Agora is passport-only for v1, so this is an assert rather than a branch. (2) *All-filler personal number rejected* — the field is optional in ICAO Doc 9303, and a country that doesn't populate it emits 14 `<` characters for **every** citizen, so without this check the first person to register would consume the country's only possible anchor value and permanently lock out the entire rest of the population (the pallet rejects a reused anchor with `AnchorAlreadyUsed`). Log #67 flagged "does the deployment country actually populate this field?" as unresolvable from the spec; this doesn't answer it, but it converts a silent population-wide failure into an immediate, diagnosable one. (3) *DG1 must be supplied as a clear value, not a hash* — `SaltedValue<T>` has a hash-only mode where `get_hash()` returns the supplied hash verbatim and `value` stays zeroed, so `comm_in` would still verify while the extracted personal number was all zeroes and every prover derived the identical identity input. This assert is what makes the commitment chain actually constrain the bytes the circuit reads; without it the fork is trivially broken.
    - **Log #67's anchor/nullifier separation is preserved structurally.** The document-bound `salted_private_nullifier` is still an input (it's needed to reconstruct `comm_in`) but its clear value is never read, and Agora's flow passes it in hash-only mode — so the per-vote nullifier stays entirely out of the anchor derivation path, matching the separation log #68 already enforced at the storage level.
    - **New, not anticipated by log #67: the obvious integration (`anchor` as a standalone on-chain proof) is unsound, and needed a fourth circuit to fix.** `anchor` proves the anchor came from the DG1 committed at `comm_in` — but `comm_in` is a **private witness** inside ZKPassport's outer circuit. It is not among that proof's public inputs (which are `certificate_registry_root`, `circuit_registry_root`, `current_date`, `service_scope`, `service_subscope`, `param_commitments`, `nullifier_type`, `scoped_nullifier`, `oprf_pk_hash` — confirmed again from `bin/main/outer/count_4/src/main.nr`, matching log #66). So a standalone `anchor` proof and an outer passport proof cannot be linked on-chain, and nothing stops a prover pairing a genuine outer proof with an `anchor` proof over a `comm_in` of their own invention — which defeats the entire Sybil check the anchor exists for. The fix is `disclosure`: same computation, but shaped to the disclosure-subproof interface the outer circuit already recursively verifies, so the anchor rides out inside the outer proof's own `param_commitments` array. One proof, one `comm_in`, authenticated back to `certificate_registry_root`. **A production `AnchorProofVerifier` must be built on `disclosure`, not on `anchor`.**

    - **`runtime/src/verifier.rs` rewritten: `RarimoGroth16Verifier` → `ZkPassportUltraHonkVerifier`, fail-closed by construction.** Every structural check is real and enforced; only the pairing check is missing, and it lives behind a one-function `mod ultrahonk` seam whose doc comment carries the full evidence above, so replacing it later touches nothing else. `verify()` returns `false` for everything today. **This is the same posture the Rarimo-era file actually shipped in** (its `verify_inner` returned `false` whenever the VK asset was absent) — preserved deliberately rather than replaced with a passthrough. `ark-groth16`/`ark-serialize` are no longer used; the verifier now needs no cryptography dependency at all for the checks it does perform (the BN254 scalar modulus is a 32-byte constant and canonicity is a byte comparison), so those workspace deps are now dead weight and should be dropped when someone touches `runtime/Cargo.toml`.
    - **The proof envelope, which is the actual deliverable here — one contract, two languages.** `zk_proof` is an 8-byte header plus bb's `proof` file passed through verbatim: `magic 0x5A` / `format_version 0x01` / `outer_count N` / `proof_variant (0 = ZK via -t evm, 1 = Plain via -t evm-no-zk)` / `proof_len u32 big-endian`. Total length must equal `8 + proof_len` **exactly** — trailing padding is rejected as hard as truncation, so a proof can never be extended with bytes the verifier ignores. Design notes worth keeping: the proof bytes are *not* re-serialized on the mobile side (bb already emits a flat array of 32-byte big-endian words; re-encoding would only be an opportunity to corrupt it, unlike the Rarimo path where snarkjs JSON genuinely had to be converted to ark-serialize points), and the header exists solely to carry the two facts the proof bytes cannot state about themselves — which circuit produced it, and which proving mode. `proof_len` is redundant with the slice length by design: it makes a length mismatch a parse error instead of a silent reinterpretation, and leaves room for trailing fields under a future `format_version`.

Rarimo's circuit consumed the DSC key unauthenticated. The extractor finds the certificate by ASN.1 *shape* rather than position (a 3-element SEQUENCE whose children are SEQUENCE / SEQUENCE / BIT_STRING, with a ≥6-element TBS), matching the strategy the rest of the file already uses and for the same reason: real SODs vary in which optional CMS fields are present.
      - `ParsedPassport.unresolved` now names, as explicit `null` fields, each input that cannot come from the chip — the CSC certificate and its `redc` params, the certificate-registry inclusion proof, the per-subproof commitment salts, and `service_scope`/`service_subscope` — so none of them can be quietly forgotten by a caller. **21 tests**, on the same fixture SOD as before: the Rarimo reference outputs (`referencePubkeyChunks`, `reference*Bits`) are no longer the target encoding so they are no longer asserted, but the fixture's *independent* ground truth (`expectedPubkeyN`, `expectedSignatureHex`) is now load-bearing, the extracted signed attributes are still verified against the fixture's real RSA signature via Node's `crypto`, and the reported hash offsets are checked by actually recomputing the digests and indexing at them.
    - **`mobile/src/chain/zkProving.ts` reshaped around the multi-circuit pipeline.** `hashToCid`/`fetchZkAsset` survive unchanged — they were never vendor-specific (still the same CIDv0 scheme as the desktop app's `hash_to_cid`), they just fetch Noir ACIR artifacts now instead of a 515MB circom key. Both `@iden3/*` imports are gone. In their place: a `NoirProver` seam (`execute` + `prove`) with `setNoirProver`/`getNoirProver` and a `NoirProverUnavailableError`, because no Noir native module exists in this project and — per log #66 — `@zkpassport/sdk` cannot fill the slot (it is relying-party QR orchestration, not an on-device SDK) while `noir_rs` ships no RN bridging. **The detail most likely to be got wrong, so it is encoded in the types rather than left to a comment: subproofs must be proved with the `noir-recursive` target (poseidon2 transcript) because the outer circuit verifies them with `verify_proof_with_type(..., PROOF_TYPE_HONK_ZK)`, while the outer proof alone uses `evm` (keccak) because it is the only one verified on-chain.** Getting that backwards yields proofs that fail with no useful diagnostic. `proveRegistration` also enforces the base-subproof *order* (`sig-check/dsc`, `sig-check/id-data`, `data-check/integrity`) since the outer circuit takes them positionally, and derives `count_N = 3 + disclosures` rather than trusting a caller's arithmetic. **11 new tests** against a fake prover cover exactly these: per-stage targets, ordering rejection, `count_N` derivation, and that the output envelope round-trips through the decoder.
