    ## The pairing-point question, resolved

    The worry was concrete: ZKPassport's outer circuit recursively verifies its subproofs, so bb attaches an 8-word pairing-point (aggregation) object to it. If those 8 words were spliced into the `public_inputs` array, every documented index would shift — `public_inputs[0]` would be a pairing limb rather than `certificate_registry_root`, and both `check_public_inputs` and `pallet-identity` would be reading the wrong fields.

    **They are not.** bb 5.0.0 carries the pairing-point object as the **first 8 words of the `proof` file**, never in the `public_inputs` file, and this holds for *every* circuit — recursion changes only the values (a genuine non-infinity point vs. eight zero words), not the location. The backend parses those words straight off the front of the proof in `ZKProof::from_bytes`/`PlainProof::from_bytes`.

    Established from real bytes by two independent routes that agree:

    - **The fork's bb 5.0.0 fixtures.** Across all six (`simple`/`rich`/`recursive` × `plain`/`zk`), the VK header's `combined_input_size` is exactly `len(pubs file)/32 + 8` — `10 = 2+8`, `11 = 3+8`, `10 = 2+8`. Dumping the first 256 bytes of each proof: `recursive_plain` opens with eight non-zero 136/118-bit limb words, `simple_plain` with eight zero words. The object is in the proof in both cases and in the public inputs in neither.
    - **ZKPassport's own compiled VK.** Decoding the three header words of the already-installed `runtime/assets/vk_zkpassport_outer_count_4.bin` (log #71's asset) gives `log_circuit_size = 22`, `combined_input_size = 17`, `pub_inputs_offset = 5`. `17 = 9 + 8`: nine semantic public inputs — exactly the documented `N + 5` for `count_4` — plus the eight pairing words bb counts separately. Cross-checked against `main/outer/count_4/src/main.nr` at the pinned commit (`d3a75ac`), whose `fn main` declares exactly those nine `pub` parameters, in exactly the documented order, and returns nothing.

    Confidence is high: this is not inference from bb's source or release notes but a measurement against the real production VK asset, corroborated by real bb 5.0.0 fixtures and by the circuit source. It did not require a satisfying witness for the outer circuit (which would need real passport data and four real subproofs), because the VK's `combined_input_size` field already encodes the answer.

    **Consequences.** `check_public_inputs`' `N + 5` model was already correct and needed no shift; `pallet-identity`'s `public_inputs[0]` (allowlist) and `public_inputs[len - 2]` (`scoped_nullifier`, `= 6 + D`) reads are unaffected, as is its `ConstU32<18>` bound — all re-checked against the finding, none changed. The module doc comment gained a dedicated section recording where the pairing object actually lives and how that was established, so the next reader does not have to redo it.

    **Pinned in CI.** New test `count_4_vk_matches_the_documented_public_input_layout` parses the production VK asset with the backend's own `VerificationKey` parser and asserts `combined_input_size == (4 + 5) + 8` and `log_circuit_size == 22`. If ZKPassport ever changes the circuit's public interface, that fails loudly rather than this file silently misreading field indices. The backend independently enforces the same invariant on every call (`combined_input_size - 8 == pubs.len()`), so the two halves are tied together at runtime as well.
