# Completed next steps log — entry 79

79. **Closed the mobile-wiring gap entries 76/77 flagged: `register_citizen`,
    `reverify_citizen`, and `migrate_oprf_scheme` are now all wired in
    `mobile/src/chain/identity.ts` against their real, current extrinsic signatures.**
    Entries 76/77 both named this the same open item ("mobile/desktop clients remain
    unwired for all three call shapes") without attempting it. Verifying that claim before
    writing any TypeScript surfaced that the gap was larger than "two missing functions":
    `identity.ts`'s existing `registerCitizen` was stale even against entry 75, let alone 76
    — it still modeled the call on Rarimo's old 5-signal Groth16 layout
    (`dg15PubKeyHash`/`passportHash`/`dg1Commitment`/`pkIdentityHash`/`slaveMerkleRoot`) and
    took only 2 arguments (`zk_proof`, `public_inputs`), with no `anchor`/`oprf_pk_hashes`
    parameters at all. Fixing it first (task step 1) was a prerequisite, not optional, since
    `reverify_citizen`/`migrate_oprf_scheme` were meant to mirror whatever the correct
    pattern was.

    ## What changed, in `mobile/src/chain/identity.ts`

    - Deleted the stale `ZkRegistration` interface and 2-argument `registerCitizen`. Checked
      first that nothing else in the codebase imported either (`grep -rn
      "ZkRegistration\|registerCitizen"` across `mobile/src` before rewriting) — only
      `identity.ts` itself referenced them, so there was no caller to preserve
      compatibility with.
    - New `RegisterCitizenParams` (`zkProof`, `publicInputs`, `outerCount`, `anchor`,
      `oprfPkHashes`) submits `register_citizen` (call index 0) with all 4 real arguments,
      in order.
    - New `reverifyCitizen`/`ReverifyCitizenParams` (identical shape to
      `RegisterCitizenParams` — `reverify_citizen`, call index 6, takes the same
      `zk_proof`/`public_inputs`/`anchor`/`oprf_pk_hashes` tuple per log #76) submits
      `reverify_citizen`.
    - New `migrateOprfScheme`/`MigrateOprfSchemeParams` (`zkProof`, `publicInputs`,
      `outerCount`, `newAnchor`, `oldOprfPkHashes`, `newOprfPkHashes` — note **no**
      `oldAnchor` field) submits `migrate_oprf_scheme` (call index 7) with exactly 5
      arguments. `oldAnchor`'s absence is deliberate and load-bearing, not an oversight: log
      #76 made `old_anchor` no longer caller-supplied at all — the pallet reads it from the
      caller's own `CitizenAnchor` entry — so a 6-argument call (the pre-log-#76 shape) would
      be wrong, not just outdated.
    - All three validate their payload locally before ever calling `getApi()`:
      `assertValidPublicInputs` (already existing, from `proofEncoding.ts`) against
      `outerCount`, plus new length checks on `anchor`/`oprfPkHashes` (exactly
      `NUM_OPRF_COMMITTEES = 5` entries, each exactly 32 bytes — mirrors
      `pallet_identity_zk::NUM_COMMITTEES`). A malformed payload now fails with a specific
      TypeScript error instead of the chain's bare `InvalidZKProof`/`CommitteeKeyMismatch`.
    - Module doc comment rewritten: no longer describes the Rarimo 5-signal layout;
      documents the log #75/#76 restructuring and why all three calls share the same
      `OuterProofPayload` shape.

    ## What changed, in `mobile/src/chain/zkProving.ts`

    - New `proveReverification`/`proveMigration`, both thin wrappers delegating straight to
      the existing `proveRegistration` orchestration — not a new pipeline. Checked why that's
      correct rather than assumed: `proveRegistration`'s body has no registration-specific
      logic in it at all (it doesn't inspect `disclosureSubproofs`' circuit names, only the 3
      base subproofs' prefixes), so the outer-proof assembly is mechanically identical
      regardless of which circuit fills the disclosure-subproof slot. Log #76 already
      established this at the circuit level for reverification ("needs no new circuit... the
      same shape `disclosure` already provides for registration") and for migration ("the
      outer circuit only cares that it received an array of disclosure-subproof-shaped
      results, not which specific circuit produced them" — `migrate-disclosure`'s 8-field ABI
      was confirmed identical to `disclosure`'s in log #77). The two new exports exist so
      call sites read correctly (`proveMigration(...)` for a migration flow, not
      `proveRegistration(...)` for one) — the doc comments explain the delegation so nobody
      mistakes it for duplicated, potentially-diverging logic.
    - `RegistrationProof`'s doc comment updated to note it's also what the two new functions
      return (kept as one type, not three, since the shape is genuinely identical).

    ## What this does and does not establish

    - **Does**: the mobile encode/submit path for all three identity extrinsics now matches
      the pallet's real, current signatures byte-for-byte in argument count and order — the
      specific gap entries 76/77 named ("mobile/desktop clients remain unwired for all three
      call shapes") is closed.
    - **Does not**: prove any of this against a live chain, a real ZKPassport proof, or a
      real OPRF committee. No NFC hardware or passport exists in this environment, and
      `zkProving.ts`'s `NoirProver` seam is still unimplemented (no native Noir prover module
      exists in this project) — so no genuine outer proof has ever been produced, let alone
      submitted through these functions. Separately, no OPRF committee service exists
      anywhere in this project (entries 73-77's still-standing blocker), so `anchor`/
      `oprfPkHashes`/`oldOprfPkHashes`/`newOprfPkHashes` remain plain typed parameters here —
      this entry validates their shape and submits them, it does not compute them. A sibling
      task is reported to be building a dev harness touching the OPRF-committee side of this
      separately; that work is not assumed to have landed and nothing here depends on it.
